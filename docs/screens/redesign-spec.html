Why warm light + cool dark works. They're separate variable blocks, so it's free to implement — but the reason it's good is that the two themes have different jobs. The trap is letting the accent drift warm in light and cool in dark — then your brand colour changes when the sun goes down. So: neutrals change temperature, the accent never does.

Foundations · 03

Spacing & rhythm

You called this out and you were right — it's a real bug, not a taste difference, and it's exactly the thing that separates "nice" from "flawless". Here is the full spec.

The bug you spotted

Inside one assistant turn, three different components each pick their own vertical gap, none of them aware of the others:

BetweenTodaySet byShould be
Paragraph → paragraph4pxmb-1 in MarkdownBody12px — one value, no exceptions
Paragraph → tool card8pxmy-2 on the tool
Tool card → tool card8pxmy-2 on the tool
Turn → turn12pxspace-y-3 on the list24px

So the gap between turns (12px) is larger than the gap between a paragraph and the tool card it introduces (8px), which is larger than the gap between two paragraphs (4px). The hierarchy is inverted — the transcript reads as one undifferentiated column, and the tool card looks glued to the sentence above it. That's precisely what you saw.

The rule

Siblings at the same level get the same gap, regardless of what type they are. A paragraph, a tool card, a diff and a todo list are all just blocks inside a turn — they get --block-gap. Turns get --turn-gap, which is double. Two numbers govern the entire transcript.

Recommended answers are preselected

Question 1 above arrives preselected because its first option is marked recommended; question 2's recommendation is shown but not preselected, because it's a multi-select and pre-ticking one box in a "pick one or more" list would quietly bias the answer. So the rule is: preselect on single-select, label-only on multi-select.

Honest caveat on how "recommended" is detected. There is no schema field for it — the convention is that the model appends (Recommended) to the option label and puts it first. So this is a string match, and it will miss a model that phrases it differently. The upside is that it costs nothing and degrades safely: no match simply means nothing is preselected. We strip the marker out of the label and render it as the pill, so the user never sees the raw text — which is already an improvement, because today it renders literally as "Exclude them entirely (Recommended)".

  • Same width as the prose. The card is a block inside the turn, so it inherits the 72ch measure and the 12px block gap — you can see it sitting in the same rhythm as the paragraphs above and below.
  • Icon badge instead of a coloured border. Today the whole card is outlined in Claude orange, which shouts. A 30px badge — amber shield for permission, blue question mark for a question — carries the same signal at a fraction of the visual weight.
  • Title in plain language, command in a code well. Today the tool name and the raw command run together in one mono line. Separating "what is being asked" from "the literal command" is what makes it skimmable.
  • Button ladder, not a row of equals. Primary action filled, secondary outlined, reject pushed to the far right and only tinted on hover — so the destructive option is reachable but never the thing your eye lands on first.

The product · 05

Background delegation

BET-374 landed on origin/main while this spec was being written — all six sub-issues merged. Your framing settles almost every open question, and forces two simplifications beyond the ones you named. The mockup is clickable.

Two different things are both called "a subagent"

In conversation both of these get called "a subagent", and confusing them is why this section reads as if it is missing a feature. Everything below is about the second one only.

Name used hereStarted byWhere you see it
Inline subagent the task tool In the transcript — a collapsed card you expand to read the child's turns. No window, no branch, and no row in the sidebar, ever. Untouched by this redesign.
Background job
a.k.a. "delegated subagent"		 the delegate tool In the rail — its own session, window, worktree and branch, nested under the session that started it. This section.

The two coexist deliberately and the model chooses per task. The rule of thumb: if you delegated it and expect a row in the sidebar, it is a background job; if you expect to read it inline, it is an inline subagent and no sidebar row will ever appear for it. This document says "job" throughout because the rail row, the branch and the worktree all belong to that one — "delegated subagent" means exactly the same thing.

The governing principle

A background job is disposable, non-critical and read-only. It reports to the main agent, not to you — and it asks once, before it exists, then never again. You get a pulsing dot and a name while it runs; that's the entire contract. When it's gone it's gone. Everything below follows from this, including two things it rules out that are currently shipped.

Consequence 1 — approve up front, the Claude Code way

You pointed at Claude Code's answer — "Background agents now prompt for tool permissions before launching… rather than the agent encountering permission blocks while running in the background." I researched whether we can do that, and we can — opencode already has the whole mechanism. This is better than any of the three options I was weighing, and it retracts what I said last round about delegation being a trust-mode feature. It isn't.

What opencode exposesWhat it gives us
POST /session accepts permission: PermissionRuleset A job's session can be created with its permissions already decided. No runtime prompting needed at all.
PermissionRule = {permission, pattern, action} with action: allow | deny | ask Per-tool, per-pattern grants — bash limited to pytest *, edit limited to tests/**, and so on.
PermissionRequest carries patterns[] and always[] When you grant "always" in the parent, we learn the exact patterns — so a job can inherit what you've already approved and only ask about the delta.

So the flow becomes: the model calls delegate, and before anything is created the parent panel shows one approval card listing the access the job needs. Approve, and the session is created with exactly that ruleset — the job never asks again because it has nothing left to ask. That's the Approve before launch state above.

This is strictly better than what I proposed last round on every axis:

OptionVerdict
Auto-allow for jobsUnattended shell execution with no oversight, silently overriding a setting the user left off. rejected
Auto-deny for jobsNearly every job dies on its first command, after burning a worktree and a session. rejected
Refuse to start when trust is offMy previous recommendation. Safe, but it makes delegation unusable for everyone who keeps prompts on. superseded
Approve the ruleset before launchNo deadlock, no override, nothing wasted, and delegation works with prompts on. recommended

It also sharpens the principle rather than breaking it. "Never interrupts you" becomes "asks once, before it exists — then never again", which is a promise you can actually reason about: one card, at a moment you're already engaged, and silence afterwards.

  • Skipped entirely when trust mode is on — there's nothing to approve, so no card.
  • Skipped when the parent's existing grants already cover the request, using the always[] patterns. The common case — you already approved pytest * ten minutes ago — costs nothing.
  • The model declares what it needs via a new argument on the delegate tool confirmed. That's the one piece of new surface, and it's what makes the card honest: it shows what was actually requested, not a guess.
  • The delegate call blocks until you answer, bounded (a couple of minutes, then treated as declined). Briefly blocking the parent turn is acceptable here — it's one prompt instead of N, at the only point where the cost is zero.

Verified against the running opencode (v1.15.12), not just the schema. Creating a session with a ruleset is accepted, persisted, and echoed back on the session object — including the catch-all wildcard form:

POST /session?directory=…
{ "permission": [
    { "permission": "bash", "pattern": "echo *", "action": "allow" },
    { "permission": "*",    "pattern": "**",     "action": "deny"  } ] }

→ 200 { "id": "ses_…", "permission": [ … ] }

Still worth pinning at implementation time: the catch-all must actually be honoured at match time. The API accepts it, but if an unmatched tool resolved to ask anyway we would be straight back to a job hanging until the 30-minute timeout with no UI — the exact bug BET-380 exists to fix. One integration test: a job whose ruleset omits bash must fail its first command, not stall.

Net change for BET-381 is a revert of its renderer half.

Disposable, taken literally

If jobs are disposable, the artefact is the branch — and a branch lives in git whether or not a worktree exists. So on terminal status the window and worktree are redundant and should be removed with the record, not left behind. That closes the orphan leak I flagged last round rather than hiding it:

  • Clean worktree → remove it and the window immediately. The commit is on the branch; nothing is lost.
  • Dirty worktree → keep both, using the refusal logic that already exists. Uncommitted work is the one thing that isn't disposable.
  • Parent gone → stop the job, then the same cleanup. Your point, and it's right: nobody is left to report to, so continuing just burns tokens.

Without this, the retention sweep prunes the job record after 7 days but never the window or worktree — so a stale window stops being recognisable as a job and silently reappears as an ordinary top-level session weeks later, with a slug for a name.

The real gap this uncovers

  • install.sh already installs the Claude CLI (official installer, idempotent on a PATH probe) — so the SSH-install path is covered today. No pre-step needed there.
  • But "pair to an existing box" skips install.sh entirely. That box may never have had the CLI. Today the Claude card spawns a pty that dies instantly, because resolveClaudeBin() probes two paths and then falls back to the bare string "claude" — which ENOENTs. The spawn's error handler is () => resolve(), so the failure is swallowed. This is the case worth building the check for.
  • Two more ways to land there: the installer's claude download is non-fatal (it warns and continues, so an install can "succeed" without it), and the documented launchd/systemd PATH trap means the CLI can be installed but invisible to the service — a different failure needing a different fix, which is why the check reports where it looked.

Worth separating two things the question conflates. launcherRegistry.mjs does list claude, codex and kimi with bin fields, and install.sh probes all three — but those are terminal-mode TUI launchers, not auth. You only need those binaries if you want to run the CLI as an interactive window; chat mode needs none of them. So availability for all three belongs in Settings → Extensions → CLI launch options as a status display, not as an onboarding gate. Onboarding gets exactly one CLI check, for Claude.

Lazy-installing the Claude CLI

You're right and my earlier objection was wrong. I argued a deferred install would land the binary somewhere the service can't see. It doesn't — I checked launchd_agent_path() and $HOME/.local/bin is appended to the service PATH unconditionally, with no reference to whether claude exists. So the directory is on the PATH of both supervisors whether or not anything is in it, and the official installer puts the binary in exactly that directory. A later install is visible to the service. No screen before the box, no flag, no compromise.

Three things make the lazy install clean rather than merely possible:

  • The PATH entry is unconditional — launchd_agent_path() composes a static list and prepends $HOME/.local/bin if absent. Both LaunchAgent plists and both systemd units render from it. Nothing to change.
  • No restart is needed. resolveClaudeBin() probes with existsSync on every invocation, so the next spawn picks the binary up. It isn't cached at boot.
  • The macOS install smoke test asserts nothing about claude — so removing the step doesn't touch CI.

And the timing cost is smaller than I framed it: a Claude user pays the same download either way, just later and visibly, as a named step rather than a silent stall inside a six-stage installer. Everyone else never pays it at all.

App.tsx stacks up to six full-width bars above the session — five UpdateBar variants (app update, update error, server update, version skew, compatibility) plus the reconnect banner. They can co-occur. The spec never mentions them, and the new spacing scale will make a pile of six read as broken chrome rather than dense chrome.

Needs a rule: at most one bar visible, by severity, with the rest collapsed into it — or moved into the session header as a status affordance.

4 · Four toast systems, and the spec adds a fifth

Screenshot-detected, agent-sent-file, systemNotice, and the desktop Notification bridge are four separate implementations with different shapes and placements. The settings redesign introduces Undo, which is a fifth. That's the moment to define one toast primitive — position, stacking, timeout, action slot, and how it behaves on mobile — rather than adding to the pile.

6 · Markdown and code, past measure and leading

The type section fixes size, leading and measure — but MD_COMPONENTS currently downgrades every heading to a <div> at near-body size, because with one mono face at one weight, real headings were pointless. With a proper type scale that decision should be revisited, and it's the difference between a transcript that skims well and one that doesn't. Also unspecced: tables, blockquotes, nested lists, images, and the Prism theme pair that light mode requires.

7 · Terminal-mode chrome

"The terminal stays dark" settles the pane. It doesn't settle the chrome around it — the session header, the mode switcher (currently a raw <select> with a hardcoded colorScheme: dark), or how a dark pane sits inside a light app without looking like a rendering bug. Terminal mode is half the product's history and gets one sentence.

8 · The mobile contract

Mobile is a separate spec — agreed. But mobile reshapes shared desktop components through manta-* hook classes and two positional [class*=…] selectors, and this redesign restructures precisely those elements. If the desktop work lands first without a stated contract, mobile breaks silently — and the mobile spec will be written against a moving target.

What this spec owes the mobile one: the final list of hook classes the shared components will expose, and a commitment that the two positional selectors are replaced by named hooks. That's a paragraph, and it unblocks the other document.

9 · How we'll know it's right

The plan has one verification mechanism — a CI contrast check — and it's the strongest thing in it. Everything else is judged by eye, across ten phases, on two clients and two themes. Worth adding:

  • Golden screenshots per theme. The harness already exists (ChatPanel.harness.test.tsx, the demo fixture, the website shots). Doubling them to light + dark makes a theme regression visible instead of reported.
  • Keyboard-path acceptance. The a11y fixes are specced for Settings only. The new tree sidebar, the ask cards and the folder picker are all new keyboard surfaces with no stated expectation.
  • A motion vocabulary. Phase 7 says "elevation and motion" and stops there. The tokens exist in the brand file; the spec never picks durations or easings, and there's exactly one prefers-reduced-motion rule in the codebase today.

The three, now settled

1 · Terminal mode in a light app — settled. decided The dark pane sits inset in a light window: sidebar, header and composer all follow the theme, with a soft inner border and a slightly inset shadow on the pane so it reads as a deliberate surface rather than a rendering fault. 2 · Heading prominence — settled: Balanced. decided h1 17px/600, h2 15px/600, h3 14px/600, with 22 / 18 / 14px of space above. Most of the effect comes from the gap, not the size, so headings read as landmarks without the transcript turning into a document. Comparison page →

Today every markdown heading is downgraded to a <div> at near-body size — rational when everything was one mono face at one weight. With a real type scale we can make them real. Quiet keeps the transcript flat and calm, which matches every other trim you've asked for. Loud (17px / 15px semibold) makes a long structured answer genuinely skimmable, which is the single biggest readability lever left after measure and leading. I lean loud, but you've consistently chosen calmer, so I won't assume.
