Resume after limit reset

Design for the quota-interruption flow: a persistent sidebar indicator, per-conversation markers, and one modal listing every conversation a subscription provider stopped — grouped by workspace, each with the model that was in flight and its cold-cache cost.

1 · The indicator

Sidebar header carries the count of stopped conversations; the rows carry a marker so you can see which ones without opening anything. Both are fed by the box-side record, so they survive an app restart. The marker clears when that conversation resumes successfully; the pill disappears when the last one does.

4 · Reset arrives — resuming, and a refusal

At the reset instant the box re-checks the provider's usage rather than firing blind, then sends the continuations a couple of seconds apart. A conversation drops off the list the moment it resumes — the sidebar is where you watch it run. One that comes back refused stays and waits for the next check, so nothing disappears silently.

What this mockup fixes

  • Wrong conversation. Today the continuation goes to whichever pane was focused when the toast appeared. Here it goes to the conversations that were actually stopped, and you can see which.
  • Unknown model. Today no model is pinned, so the resumed turn runs on the server default. Here each row shows and locks the model that was in flight.
  • Invisible cost. One vague warning becomes a per-conversation number and a batch total.
  • Lost on close. The record lives on the box, so the pill and the markers are still there after a restart — and the iOS client can adopt the same list later.
  • Blind firing. The batch waits for the provider's usage to actually report recovered, instead of a fixed offset, and a refusal re-queues rather than being dropped.

Accepted trade-offs

  • The continuation text is still the literal "Keep going" — no reference to what was interrupted.
  • A conversation whose reset already passed while the box was asleep resumes on wake, however late that is.
  • Two of the three providers are detected on vendor prose, which will drift. The usage-meter correlation exists so a reworded message degrades the feature instead of breaking it.

Build it out of the primitives that already exist — do not hand-roll

The CSS in this file exists so the mockup renders standalone. It is not the implementation. Every visual below already has a component; the classes here map onto them one-for-one. A new bespoke button, checkbox, chip or dialog in this feature is a review defect.

Type, spacing and colour — all on existing scales

  • Every size in this file is var(--sp-*) and every radius var(--r-*). Nothing off-grid was introduced; use the Tailwind equivalents (p-3, gap-2, rounded-md) rather than raw pixels.
  • Font sizes map to the eight named roles: 11px = text-micro, 12px = text-meta, 13px = text-label, 14px = text-body, 17px = text-title, 24px = text-display.
  • Colours are tokens only — --tx1..4, --warn, --ok, --danger, --accent, --border*, --fill*. No new token is required for this feature. If you think you need one, you have drifted from the design.
  • The only values deliberately not on a scale are the mockup's own framing (sidebar width, modal body max-height) — those come from the real components, not from here.
