# Astra spec review

The swallowed rejection and discarded result are correctly identified on both manual handlers. Reusing the existing toast store/helper pattern is appropriate; no additional library is warranted. The proposed state and outcome contracts need the corrections below.

1. **BLOCKING — `ok:false` does not prove expiration or that no job started.** Evidence: `src/server/rpc.mjs:2475-2480` also returns false when the engine is absent; `src/server/delegate.mjs:2495-2504,4840-4841` returns false for any previously resolved entry, including an approval accepted from another client. A successful request whose response was lost followed by a retry likewise returns false while the job may already be running. Spec lines 73 and 76 would falsely reassure the user, or encourage starting a duplicate job. **Exact change:** classify a valid false reply as `unavailable`, not `expired`. Recommend an informational toast for Decline (not silence): “This approval is no longer available. Check background jobs to see whether it was already started.” Approve should similarly say the approval is no longer available and direct the user to check jobs before retrying. Do not assert a reason or job outcome the unchanged wire cannot establish. Treat malformed replies as failures/unknown outcomes, not as expiration. Update the copy, tests, and acceptance criteria accordingly.

2. **BLOCKING — optimistic hiding does not prevent duplicate actions or stale resurrection.** Evidence: `src/renderer/ChatPanel.tsx:946-968` unconditionally reinstalls the first nonempty poll result and ignores empty results. A poll can restore the same request while the decision RPC is in flight, or a delayed pre-decision poll can restore it after successful resolution. The latter card persists because empty lists never clear it. The spec changes only handlers and so preserves both races, contradicting lines 66 and 180. **Exact change:** add synchronous per-approval in-flight protection shared by handlers and polling; suppress decided IDs and invalidate stale poll responses across decisions. Reconcile an authoritative empty list with displayed stale approvals. Preserve the 3-second cadence; changing poll result handling is necessary scope, not a polling-cadence change. Specify how a failed/uncertain decision becomes retryable without permitting an older poll or older decision completion to overwrite a newer approval.

3. **BLOCKING — retain edited grants on failed Approve.** Evidence: `src/renderer/PanelCards.tsx:595-603,685-687` keeps the edited rules locally and passes their current value to the parent. Unmounting then restoring the original approval resets them. A user who removed broad access can press “try again” and unintentionally approve the original broader access. The spec's claim that preservation requires hoisting all card state is incorrect: the callback already receives the submitted rules. **Exact change:** snapshot `tools` at the click and restore `{ ...approval, tools: tools.map(t => ({ ...t })) }`; retain that snapshot against poll updates and remounts for the request until resolution. Alternatively keep the card mounted in an explicit disabled pending state. Recommendation: preserving edited grants is required, not an acceptable loss. Test narrowing an access pattern, rejecting the call, and verifying that a subsequent approval submits exactly the narrowed rules.

4. **SHOULD — failure copy must express uncertainty rather than assert a pending request.** Evidence: `src/renderer/api/httpApi.ts:323-348` can reject on network, authentication, HTTP errors, and invalid/failed responses; `src/server/delegate.mjs:2485-2504` independently expires or resolves entries. A request can be committed before its response is lost. Thus “the box didn’t respond” and especially “It’s still waiting” are not supported for every rejection. **Exact change:** use safe copy such as “Couldn’t confirm that the background job was declined. Check background jobs before trying again.” and the equivalent approval wording. A restored card represents an unconfirmed retry opportunity, not evidence that the server still has a pending entry; reconcile it when the next authoritative poll succeeds.

5. **SHOULD — the session guard must match actual panel lifetime.** Evidence: `src/renderer/App.tsx:2205-2225` keeps one mounted panel per visited session with stable `sessionId`, switching `isActive` instead. `src/renderer/ChatPanel.tsx:946-968` resets the approval when activity changes. A `sessionIdRef` alone therefore still restores the old hidden panel after navigation, contrary to spec lines 81-82. **Exact change:** capture an effect/lifecycle generation that changes on session, activity, trust-mode changes and unmount; restore only in the matching live generation (and only when it cannot overwrite a newer request). On reactivation let the current poll reconcile. Test navigation via `isActive`, not only by replacing `sessionId`, plus unmount and an intervening newer approval.

6. **SHOULD — bound the decision request, or explicitly handle a stalled request.** Evidence: `src/renderer/api/httpApi.ts:300-305,363-376,1314-1316` uses unbounded RPC for these immediate server-side mutations; a never-settling fetch produces neither a result nor the proposed error/restore feedback. **Exact change:** permit the narrow `httpApi.ts` edit to use its existing bounded RPC helper for approve/decline (no wire or API type change), with the timeout classified as uncertain failure. Test a stalled call and its eventual timeout. These calls only resolve an approval; they do not wait for job creation, so the long-job rationale for unbounded RPC does not apply.

7. **BLOCKING — require a handler-level regression test; remove the fallback waiver.** Evidence: spec lines 162-169 permit skipping the only tests that exercise the actual defect; new-helper tests alone cannot show that today's handlers change behavior. `src/renderer/ChatPanel.background.test.tsx:94-121` already mounts ChatPanel with API overrides, and `src/renderer/testHarness.tsx:112-126,310-340` supports overridden methods and rerendering. The poll runs immediately on mount, so this is feasible without waiting 3 seconds. **Exact change:** require component tests driving Decline/Approve through the real card and asserting toast-store updates, visibility, and RPC arguments. Include rejected/false/success cases, in-flight and late poll races, edited-grant retry, and the actual inactive-panel switch. At least the rejection/false click tests must run unchanged against the original code and fail behaviorally, rather than failing because a new helper import is missing. Remove the “if the harness cannot … rely on tests 1–7” exemption.

VERDICT: CHANGES REQUIRED

### Scope judgment

The main growth is justified **given the retained optimistic-hide design**. Per-approval in-flight/retry state prevents duplicate decisions and preserves access edits. The epoch rejects a poll issued before an uncertain decision finished (including an old empty result that would immediately erase the restored retry card). The lifecycle generation stops restoration after navigation even when the user leaves and returns before completion. These protect different races; they are not three copies of the same guard. Keeping a disabled card mounted could reduce some of this machinery, but switching designs now is optional, not required to approve this fix.

The 14 component cases cover meaningful outcomes and races, not excessive implementation details. Parameterize symmetric approve/decline cases rather than writing 14 large independent setups. The duplicate helper outcome tests and permanent settled records are the parts worth trimming; no broader state-machine framework, new hook architecture, or server protocol is needed.

### Findings

1. **SHOULD — cut permanent settled tombstones if keeping completion-epoch invalidation.** Evidence: spec §3.3 lines 110–115 and §7 lines 296–300; `src/server/delegate.mjs:2489-2504` removes the pending entry synchronously before the decision reply. Every poll issued before completion is already invalidated by the completion epoch. A poll issued after a successful decision cannot truthfully list that ID. Suppressing it forever adds session-lifetime retention and tests of impossible fresh server responses, rather than additional protection against the actual late-response race. **Exact change:** retain map entries only for in-flight and retry snapshots; delete on confirmed completion, with epoch invalidation unchanged. Rewrite cases 2/3 to resolve a genuinely pre-existing deferred poll, not to make a fresh post-completion server query invent a settled approval. Case 9 already tests the relevant race. Keeping the tombstones is not a correctness blocker, but it is unnecessary defensive state under this wire contract.

2. **SHOULD — make sibling-branch ownership explicit rather than claiming both landing orders are independent.** Evidence: spec lines 63–68 and 303 say this change does not edit auto-cover; lines 163–170 explicitly replace the whole post-fetch body without auto-cover. The current `ChatPanel.tsx:956-961` still contains it. Thus implementing the instructions on this worktree does remove the sibling feature before that sibling merges. **Exact change:** land/rebase on `desktop-approval-pending-always` first, then modify the reconciler against that base. Alternatively explicitly declare that this PR incorporates the already-agreed deletion and coordinate ownership. Do not call the conflict purely textual while the branches independently change behavior. This is integration/scope clarification, not a need for more code.

3. **SHOULD — qualify the timeout guarantee and make its mock realistic.** Evidence: `src/renderer/api/httpApi.ts:257-269` clears the abort timer when `fetch` returns headers; `rpcInner` reads `res.json()` afterward (`:338`). The reused helper bounds waiting for response headers, not a stalled response body. Spec lines 286 and 272–275 currently promise a fully bounded call, and a mock promise that simply never settles will not reject merely because its signal was aborted. **Exact change:** specify that the fetch mock observes `init.signal` and rejects on abort. Qualify this change as using the existing 15-second fetch timeout; if full response-body timing is a hard acceptance requirement, explicitly scope a timeout around the complete approval RPC rather than silently claiming the existing helper provides it. Avoid an unrelated global timeout-helper rewrite in this fix.

4. **NIT — reduce redundant unit coverage, not behavioral coverage.** Evidence: spec §5.1 covers all six decision outcomes through the real handlers; §5.2 repeats the full outcome × kind matrix through the helper. **Exact change:** keep component outcome/copy checks authoritative; unit-test only the malformed-reply classification edges and reconciliation logic that are awkward to exercise through the UI. Parameterize symmetric component cases. This reduces maintenance while retaining the meaningful regression and race checks.

No new blocking correctness or security issue found in the revised decision/restoration design. Implementation review should confirm snapshots are captured at click (as §3.5 requires), and that reconciliation uses current refs/state rather than stale closures.

VERDICT: APPROVE
