# Astra review — desktop-approval-pending-always

## Findings

1. **SHOULD — Make the security regression's ordering deterministic.**
   Evidence: spec lines 125–134; `src/renderer/ChatPanel.tsx:942–960`; `src/renderer/hooks/useSseBus.ts:394–403`; `src/renderer/testHarness.tsx:327–336`. The initial poll starts during mount, initial permission hydration can replace an emitted permission list, and `h.flush()` only advances zero-delay tasks: calling it twice does not exercise a 3-second tick. An immediately resolved approval mock can therefore display the card before the malicious pending ask arrives, allowing the unfixed code to pass a prematurely evaluated assertion.
   **Exact change:** prescribe a deferred promise for `delegatePendingApprovals`. Complete initial hydration, emit and flush the permission frame (including its ref-sync effect), then resolve the held approval response inside `act` and assert zero approvals plus the visible card. Also test a later poll with controlled timer advancement if desired; do not use two `h.flush()` calls as a substitute for advancing 3 seconds. Use the actual button label `Start job` (`PanelCards.tsx:684–689`). Keep the required red-on-base check, confirming failure is the unexpected approve call rather than a missing-label assertion. For the click test, resolve `delegateApprove` successfully and assert eventual dismissal, avoiding assumptions about optimistic dismissal owned by the separate feedback branch.

2. **SHOULD — Record a separate, concrete server-side consent bug found during the sibling audit.**
   Evidence: `src/renderer/PanelCards.tsx:650–655,684` allows removing every rule and submitting `[]`; `src/server/delegate.mjs:4787` uses `Array.isArray(edited) && edited.length > 0 ? edited : tools`. Thus a user who removes all access and clicks Start actually grants the original tool-supplied access again. This is not another unanswered-ask auto-approval: it requires a click, but silently overrides the user's reduced grant.
   **Exact change:** add a separately tracked security follow-up in §7: honor an explicitly supplied empty array (fall back only when edited tools are absent), and test that approving `[]` creates a child with only the catch-all deny. Do not put its implementation or card changes in this renderer-removal patch or the unrelated button-failure-feedback patch. Static code evidence establishes the fallback; no live job was launched during this review.

3. **NIT — Narrow the invariant and strengthen the recorded audit evidence.**
   Evidence: spec lines 70–76; `src/server/delegate.mjs:4771–4776` intentionally starts no-tool jobs without a card; `src/server/index.mjs:2793–2801` explicitly supplies trust for consented overnight work; `ChatPanel.tsx:3140–3144` necessarily approves from a client click. “No client-side path may approve it” is literally inconsistent with Start, and “only the user's click starts the job” overstates the coverage of a desktop pre-flight fix.
   **Exact change:** say “For a pending pre-flight approval, no renderer path may approve automatically; approval requires an explicit user action.” Replace the iOS helper-name-only grep rationale with the call-site audit below. Name `desktop-delegate-decline-feedback` as the existing owner of Start/Not now failure handling in §3.5/§7 rather than proposing a new fix. The current spec already excludes those handlers from implementation; preserve that separation.

## Security review conclusions

- **Root cause confirmed.** `permissionFromV2` copies proposed `save` patterns into `always` (`src/shared/opencodeV2.mjs:471–490`). Both initial permission hydration and live frames contain pending asks (`opencode.mjs:1502–1509`; `useSseBus.ts:394–403,739–745`). The removed helper is the production consumer treating those proposed patterns as existing authority (`chatUtils.ts:2261–2281`). Removing its sole production call and deleting the helper closes this automatic approval path.
- **Removal is preferable to wiring saved rules in this hotfix.** The spike evidence proves saved rules exist (`docs/opencode-v2/spikes/p3/FINDINGS.md:153–160`; `docs/opencode-v2/spikes/round1-b.md:240–253`), not that they authorize delegation into a separately scoped child. In particular, the live trust-mode pump saves `always` decisions without a per-ask human action (`permissionAskPump.mjs:71–86`); those records cannot establish the user-grant provenance this proposed reuse requires. Keep saved-rule support separate, with project scope, aliases, rule precedence and provenance resolved before implementation.
- **Box approval flow:** REST creation derives trust from server config, not the tool request body (`index.mjs:4517–4530`). Pending requests are only resolved by approve/decline or timeout (`delegate.mjs:2486–2509,4840`); neither server resolver examines pending permission `always`/`save`. REST and RPC approval entry points simply resolve an explicit authenticated request (`index.mjs:4442–4450`; `rpc.mjs:2475–2482`). Their common bearer authorization is not proof of a human click, so this fix should claim removal of automatic client consent, not a new server-enforced human-origin boundary. Requiring a prior list read would not establish human intent either.
- **Other automatic permission handling:** `permissionAskPump.mjs:68–97` auto-replies only under configured trust mode, and otherwise forwards the ask. The renderer's ordinary permission cards display `always` as the scope of a user-selectable button, not as authority (`Cards.tsx:210–239`); the shared desktop/CTO reply helper forwards that explicit selection (`chatShared.tsx:641–661`). No second production auto-cover consumer was found.
- **Native iOS:** searches covered delegate/approval/always and permission-reply call sites, not just the deleted helper name. There is no delegate pre-flight approval API/card in the native client found by this audit. Ordinary permissions are answered through the card's button closure (`ChatScreen.swift:1735–1736,1758–1760`), the store forwarding method (`ChatSessionStore.swift:1146–1151`), or a selected notification action (`MantaAppDelegate.swift:116–133`). The decoded `always` field is not used to auto-grant. The unused `replyToLatestPermission` helper also requires an explicit decision argument; it does not derive authority from an ask. Native `try?` failure swallowing is a separate feedback problem, not evidence of automatic consent.
- **Scope:** no changes to Start/Not now callbacks or `PanelCards.tsx` are necessary here. Existing session-change cancellation and active-panel gating remain intact. Poll failures remain fail-closed; stale-card/feedback behavior belongs to the other spec. No new library is justified for removing an invalid trust decision.

Read-only review apart from this report. No tests or live permission/job actions were run.

**Counts:** 0 BLOCKING, 2 SHOULD, 1 NIT.

VERDICT: APPROVE
