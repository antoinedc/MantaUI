# Review: desktop auth reconnect link

1. **BLOCKING — Accounts does not currently offer the promised re-sign-in for existing Claude/Codex seats.**
   - Evidence: spec §§1–3 claims the expanded panel is where users can re-sign-in. `src/renderer/SeatsPanel.tsx:182-278,337-370` instead offers rename, switch, remove, Add seat, and Add account; there is no existing-seat re-sign action. Add is not a substitute: `src/renderer/AddSeatFlow.tsx:66-67` tells a returning user to use a different account, and `src/server/accountsManager.mjs:337-372` rejects duplicate identity. Both providers have explicit duplicate-rejection tests (`accountsManager.test.mjs:475-488,713-721`). A sole seat cannot be removed (`SeatsPanel.tsx:191-196`); externally managed Claude also has no Disconnect (`AccountsCard.tsx:455-458`). This is a genuine recovery dead end, even though opening the modal is visible.
   - A real existing flow was missed in the reuse analysis: `src/renderer/ResignSeatFlow.tsx:62-139` calls `accountsResignSeat({provider,seatId})`, preserving the existing seat and verifying account identity. It is already wired from `UsageDial.tsx:137-147,380-387,530`, not from Settings. Server support exists (`accountsManager.mjs:979-996,1128-1130`); no new OAuth implementation is required.
   - **Exact change:** revise the design to expose the existing `ResignSeatFlow` on each existing seat in the Accounts panel, including a single seat. Keep the provider-focused navigation, but make the destination genuinely actionable. Allow explicit re-sign-in even when a newly failed credential has not yet been marked logged out by the usage poller. Define the no-seat-view fallback too: an externally managed connected Claude row cannot be assumed to offer Connect. Either provide a working existing sign-in entry point for that case or show explicit actionable recovery instructions; do not silently land there claiming recovery is available. Amend the renderer-only scope to include this minimal destination wiring and add same-account recovery acceptance criteria.

2. **BLOCKING — Keeping the banner exposes stale reconnect metadata on unrelated later errors; the specified clearing lifecycle is incorrect.**
   - Evidence: `src/renderer/hooks/useSseBus.ts:233-241` has a public error setter that never clears auth metadata. The dismiss button only invokes that setter (`ChatPanel.tsx:3206`), contrary to the spec's assertion that both fields clear together. New sends clear text (`ChatPanel.tsx:1668`) and can later set unrelated transport failures (`ChatPanel.tsx:1923`). After the proposed non-clearing navigation, those failures can therefore retain the previous provider's Reconnect button. `useSseBus.ts:568` clears only an Aborted banner on running; its retry branch (`595-616`) does not clear auth errors at all. The promised “next busy/retry frame” lifecycle is not current behavior.
   - **Exact change:** make every general `setSendError` write invalidate reconnect metadata, with the classified `sessionError` branch setting the new matching metadata after the text. Preserve both only for the navigation press. Document that an ordinary send clears the banner at submission; do not claim all busy/retry frames clear it unless intentionally implementing that change. Test auth failure → Reconnect → dismiss/new send → unrelated failure and assert no Reconnect; also test another classified provider error replaces the target. This is directly within the banner-state change, not an unrelated refactor.

3. **SHOULD — Verify the destination, not only the event, and explicitly bound non-seat-provider behavior.**
   - Evidence: the proposed tests prove an event fires but would all pass with the broken destination in finding 1. The cited existing tests (`ModelMenu.test.tsx:71-103`, `UsageDial.seats.test.tsx:153-168`) also only observe dispatch; neither mounts App and proves it opens Settings. The hook harness already exposes mutable `providerID` (`useSseBusFrames.test.tsx:41,57,96`), so there is no justification for skipping OpenAI/Kimi cases.
   - Provider coverage: only Anthropic, OpenAI and Kimi receive this banner (`chatUtils.ts:1777-1781,1817-1827`). Other providers can report `ProviderAuthError` but currently fall through without this button; distinguish that existing limitation from the scope of this fix. Kimi genuinely has a recovery route without seats: the subscription row offers Disconnect when connected and Connect when disconnected (`AccountsCard.tsx:459-509,704-724`), and `ConnectProvider.tsx:662-698` renders the API-key form and saves the key. Thus opening Accounts for Kimi is not inherently a dead end, unlike the current existing-seat route. However, the spec should say to disconnect then connect with a replacement key, rather than imply that opening Accounts itself reauthenticates anything. Do not apply this fallback indiscriminately to arbitrary providers/custom endpoints.
   - **Exact change:** require all three provider navigation cases, banner persistence, repeat press, and a destination-level test exercising existing-seat re-sign-in plus Kimi's disconnected/connected recovery entry. Prove pending provider focus is consumed when Accounts mounts and when already mounted. Use a manual running-app check or an App integration test for the modal-opening criterion, rather than citing event-only tests as that coverage. State the unknown-provider/no-seat fallback and any loading/error outcome explicitly.

The missing-event-listener root cause is verified, and reuse of `openAccountsSettings` is appropriate. It is not sufficient to deliver the recovery promised by the current spec.

VERDICT: CHANGES REQUIRED

## Round 2

Reviewed revision 2 under the orchestrator's decision to defer live-login re-sign-in. Round-1 finding 1 is resolved for identified non-live seats and the explicitly deferred live-login case; finding 2 is resolved by the paired-state setter contract; finding 3 is resolved by the expanded destination and manual-navigation checks. The existing modal's portal, focus handling and Settings Escape deferral support the proposed nesting. Reusing `ResignSeatFlow` and giving live-seat instructions is appropriately scoped; a new OAuth flow or server credential replacement is not needed for this change.

1. **SHOULD — Bound the “every non-live seat works” claim; unidentified seats can never complete same-account verification.**
   - Evidence: revised spec §3.3:113-115 says the server “only refuses live seats”, and §6:230-232 promises working same-account recovery for every non-live seat. `src/server/accountsManager.mjs:613-625,645-660` also refuses an unverifiable identity: Claude needs a stored account UUID or email; Codex needs a stored account UUID. `accountsManager.test.mjs:1103-1118` explicitly proves a non-live Claude seat with neither identifier can start the flow but always ends `login-failed`. `SeatView` (`src/shared/types.ts:2356-2370`) does not expose account UUID, so checking `email` in the renderer would wrongly hide valid Codex recovery. The reused flow does produce a visible failure (`ResignSeatFlow.tsx:48-60,314-325`), so this is not another silent button and does not block the scoped navigation fix; however, its generic “try again” cannot repair that particular state.
   - **Exact change:** replace “the server only refuses live seats” with “non-live seats may attempt the existing flow; the server verifies identity and reports failure”, and qualify the success acceptance criterion to identified seats. Add one destination failure test for `login-failed`/unknown identity proving the failure remains visible and Close works. Record the missing-identity recovery limitation alongside the live-login follow-up. Do not invent a renderer capability predicate from email or expose identity fields/add a server API merely to satisfy an overbroad acceptance sentence.

2. **SHOULD — Drop the speculative Codex-live success gate; the current code already establishes that Disconnect → Connect is not an existing-seat recovery path.**
   - Evidence: `src/server/rpc.mjs:2277-2304` removes provider auth and restarts opencode; it does not remove the accounts registry. `AccountsCard.tsx:727-732,498-503` refreshes the seat list and routes a seat-bearing provider's Connect through `AddSeatGate`. The duplicate rejection remains in `accountsManager.mjs:341-366` and is pinned for Codex by `accountsManager.test.mjs:713-721`. A renderer test with stubbed success cannot prove a real same-account recovery path. Spec §5.7 leaves the implementer an unnecessary open-ended investigation and creates an incentive to over-build beyond the accepted scope.
   - **Exact change:** choose the already specified honest Codex-live fallback now (“This is the login this box itself uses; it can't be re-signed from here yet”), record the server follow-up as the accepted decision rather than a pending maintainer question, and test that copy with no Sign back in button. Remove §5.7's speculative success gate. Keep the Kimi Disconnect → Connect test: it has no seat registry and uses the real API-key form, so that is a different and valid path.

No remaining blocking findings under the accepted scope. The new non-live-seat button invokes the existing recovery flow, whose success, failure and cancel outcomes are visible; live seats must not render it. Retain the planned disabled state during another local sign-in and the running-app stacked-modal check.

VERDICT: APPROVE
