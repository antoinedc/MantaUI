# WS11 — Server consolidation

Status: draft · Date: 2026-10-28 · Branch: `feat/ios-desktop-parity` · Wave: **D** (runs alone, after C-int)

## Goal

D23 makes the box the only owner of logic. Waves A–C ported desktop logic into
Swift (WS01, WS03, WS04, WS08, WS10, plus older ports). WS11 moves every
MOVE-NOW item that `server-first-audit.md` §3b assigns to WS11 onto the box,
switches the **desktop** to the box result and deletes the desktop copy, then
switches **iOS** and deletes the Swift port. No parallel implementations, no
parity fixtures, no "fallback for old boxes" (D24).

Items in scope (audit IDs): **U1** T1, T2, T4, T5, T8, T16 · **U2** S1, S2, S3,
S8, S10, S13, S14 · **U3** T20, T21, X1, X3, X5, X6, X9 · **U4** K2, K3, K5, K7 ·
**U5** capabilities + guardrails. Every MOVE-LATER item is listed in
[Follow-ups](#follow-ups-move-later-tickets).

Because WS11 runs alone it may edit any file (server, desktop renderer, iOS app,
`Package.swift`, `project.yml`). It still follows ground rules 1–5 and C1–C7.
`MantaUI.xcodeproj/project.pbxproj` is regenerated by the orchestrator at the
end (D18), never by the worker.

## Ground rules specific to WS11

1. **One module per family, node-tested.** Each sub-step adds its own server
   module + `*.test.mjs`. Channel registration in `src/server/rpc.mjs`, routes
   in `src/server/index.mjs` and edits to `src/server/streamInterp.mjs` are done
   by the worker (sole worker in wave D, D24).
2. **Additive wire only (K2).** New channels, new response/frame fields, opt-in
   request flags. No existing field changes meaning. An old desktop on a new box
   keeps working unchanged.
3. **Capability-gated clients (D24).** Every moved surface checks one box
   capability id (D1). Missing → the surface follows the no-dead-control rule
   (hidden, or disabled with **"Update your box to use this"**). No copy of the
   old client logic is kept for old boxes.
4. **Box text uses the desktop wording** unless this spec names a change. Where
   desktop and iOS disagreed, the chosen rule is stated and called out under
   [Behaviour changes](#behaviour-changes-to-call-out-in-the-pr).
5. **Time-relative text keeps a box instant** and the client compares it to its
   own clock (T21 `staleAt`). Exception, accepted by the audit: K3 health lines
   are worded at response time (they are polled).
6. **Sub-steps are reviewed one at a time, in order.** Each D-n (or each
   release-atomic group below) is implemented, reviewed and committed on the
   branch on its own. A later step MAY extend shared modules an earlier step
   created or touched — `transcriptView.mjs`, `streamInterp.mjs`, `rpc.mjs`,
   `index.mjs`, `boxCapabilities.mjs` (+ test), `TranscriptViewModels.swift`,
   `ChatSessionStore.swift`, `MantaStreamModels.swift`/`MantaEventStore.swift`,
   `httpApi.ts`, `types.ts`/`api.ts`, `serverFirstGuard.test.mjs` — additively,
   and never changes a contract an earlier step shipped without updating its
   consumers in the same step.
   **Release-atomic groups:** D8+D9 (one capability, `transcript-view-1`,
   appended at the END of D9 — never advertised with only the D8 fields).
   Every other step is atomic by itself.
   **Per-step gate** (before the step's review): `npm run typecheck`,
   `npm run test:server`, the vitest files the step touched
   (`npx vitest run <files>`), and `mobile/native/verify.sh` (Foundation
   package, D19). For a step that changes app-only Swift (views/stores), also
   `ios-mantaui` `compile-only`. **Combined gate** (after D11): full
   `npm test`, `npm run typecheck`, and `ios-mantaui` `test-unit` (merge gate).

## D1 — Capabilities list + guardrails (U5)

### State at the start of wave D (built in wave B/C)

The capability list already exists (master D25, WS02 SF-0):
`src/server/boxCapabilities.mjs` exports `BOX_CAPABILITIES`; `GET /api/version`
(`writeVersionResponse`, `version.mjs`) and `server:version` (`rpc.mjs`, M-02-srv-1)
return it as `capabilities: string[]`. It carries every id in the master's
"Capability id registry" (wave B: 02/07/09/06; wave C: 05). The single client
accessors are WS02's iOS `MantaAPIClient.boxCapabilities() -> Set<String>`
(+ the chat-scoped `ChatCardCapabilities` store) and desktop
`src/renderer/hooks/useBoxCapabilities.ts` → `useBoxCapability(id)`.
Specs 05/06/07/09 detect old boxes by an exact response-shape / unknown-channel
signal; their ids are registered but not all read.

### Wire contract

- No new module and no rename: D1 EXTENDS `src/server/boxCapabilities.mjs`
  (the name already differs from `src/server/capabilities.mjs`, the plugin
  capability-job queue). Each later sub-step appends its id(s) to
  `BOX_CAPABILITIES`. `version.mjs` / `rpc.mjs` already return the list — no
  edit needed beyond what each sub-step registers.
- **Only `GET /api/version` is upgrade-exempt** (`isUpgradeExemptPath`,
  `src/server/upgradeV2.mjs:82-90`); `/rpc/server:version` answers
  `503 {"error":"box upgrading","upgrade":true}` while the box migrates. So in
  wave D BOTH clients read capabilities from `GET /api/version` (authenticated,
  same bearer), never from the `server:version` RPC (which keeps returning the
  list for old callers, unchanged). No server change is needed: WS02 already
  returns `capabilities` from `writeVersionResponse` (M-02-srv-1 / D25).
- Ids are lowercase `kebab-name-N` (`/^[a-z0-9-]+-\d+$/`, the master registry
  format); an id is never reused for a different shape. A shape change ships a
  new id (`…-2`) and keeps the old one until clients drop it.

### Client behaviour (both clients)

- The list is fetched with `GET /api/version` on connect, on every reconnect of
  the event stream, and on box switch. Unknown ids are ignored.
- **Three states, never conflated:**
  | State | When | Gated surfaces show |
  |---|---|---|
  | `loading` | first fetch in flight | their loading state |
  | `loaded(ids)` | 200 with a body; a body WITHOUT `capabilities` = old box = empty set | the feature, or the "update" note when its id is absent |
  | `failed` | transport error, timeout (5 s), non-2xx other than 401 | their "Couldn't reach your box" / retry state — **never** the "update" note (a failure is not evidence of an old box) |
  A 401 follows the existing sign-in path. `failed` retries with backoff
  1 s → 2 s → 5 s → 10 s (cap), and immediately on the next stream reconnect;
  the last `loaded` value is KEPT across a later failed refresh (a reconnect
  blip does not hide features).
- **Missing capability → the dependent surface is hidden, or rendered disabled
  with the static note "Update your box to use this"** (and, on iOS, a "Box
  updates" link to `MantaRoute.settings(section: "general")`). The table per
  sub-step lists which. A surface is never left as a control that does nothing.
- **The upgrade gate never waits on the list.** It is self-describing: it uses
  `GET /api/upgrade`'s `view` when present (D3 X5) and the old rendering when
  absent, so a client that connects mid-migration (list still `loading`, or
  `failed`) still gets Retry/Rollback when the box allows them.

### Wire contract

**`cache` frame** (`{kind:"stream", sub:"cache", sessionId, payload}`), payload
gains two fields:

```ts
{ isStale: boolean, idleMs: number, staleTokens: number, ttlMs: number,   // unchanged
  lastCompleted: number | null,   // NEW epoch ms of the last finished step
  staleAt: number | null }        // NEW epoch ms when the cache goes cold; null = never (not eligible)
```

`staleAt = lastCompleted + ttlMs` when `!running && lastCompleted != null &&
staleTokens >= STALE_CACHE_MIN_TOKENS`, else `null`. New pure
`computeStaleAt({lastCompleted, ttlMs, cachedTokens, running, minCacheTokens?})`
in `src/shared/streamInterpretation.mjs` (box-run; `computeStaleCache` keeps
its current output and now also returns `lastCompleted`/`staleAt`).

Emission changes in `streamInterp.mjs`:
- keep the step-end emit;
- **NEW** emit at the running→false edge (`emitRunning(sid, st, false)` and
  `emitTurnComplete` with `complete:true`) — this is the emit that carries a
  non-null `staleAt`;
- **NEW** replay in `snapshotState()` for every session with `lastCompleted`;
- **NEW** `setCacheTtlLabel(label)` on the interpreter, called from the
  `config:update` handler in `rpc.mjs` when `cacheTtl` changes (today the label
  is read once at boot, `streamInterp.mjs:223-231`), re-emitting `cache` for
  known sessions.

**NEW channel `opencode:cache`** — `args: [sessionId]` → the same payload
computed from the persisted transcript (last assistant `time.completed`, its
`tokens.cache.read + write`, the configured TTL, `running` from the interpreter),
or `null` when no assistant turn has completed. Mirrors `opencode:context`
(`rpc.mjs:1322`). Never throws for a valid id; unknown session → `null`.

**`context` frame + `opencode:context`**: computed against the **selected**
model. NEW `src/server/sessionContext.mjs`:

```js
// resolution order: model-prefs session record → config.defaultModel → last-used (st.model / transcript)
export function contextModelFor({ sessionId, prefs, config, lastUsed }) → { providerID, modelID, basis: "selected" | "default" | "last-used" } | null
```

Payload gains (additive): `limit: number | null`, `model: {providerID, modelID} | null`,
`basis: "selected" | "default" | "last-used"`. The interpreter keeps the last
step's tokens per session (`st.lastStepTokens`) and exposes
`reemitContext(sid)`; `model-prefs:set` (`rpc.mjs:2418`) calls it after a write
for that session, and `config:update` calls it for all known sessions when
`defaultModel` changes. Prefs are read through `modelPrefs.mjs`
`getModelPrefs()`, cached in memory and invalidated by `model-prefs:set`/`seed`.

- `tmux:list` and `sync:snapshot` windows gain
  `job: { id, status, parentWindowIndex: number | null } | null` —
  `computeJobNesting` moved verbatim (display parent, lift to top-level
  ancestor, cycle-safe), joined in the `syncState` listProjects wrapper from the
  delegate store (WS02's `delegateView.mjs` job lookup); `delegate.updated`
  triggers `syncState.refreshNow()`.
- NEW stream frame `windowStatus` — `{kind:"stream", sub:"windowStatus", sessionId, payload}`:

  ```ts
  { running: boolean,        // own turn
    busy: boolean,           // own turn OR any running child / background job beneath (sessionsWithActiveWork)
    startedAt: number | null,
    attention: "question" | "permission" | null,
    subagents: number,       // direct children whose OWN session is running (see below)
    stopped: boolean }       // usage-stopped store
  ```

  **Sources (authoritative only).** `liveChildStatus` is NOT used: it is set
  idle when a task tool completes (`streamInterp.mjs:489-503`), including a task
  that merely launched background work whose child keeps running. Instead the
  aggregator (`createSessionStatus` in `sessionStatus.mjs`, dependency-injected)
  keeps three maps and derives everything from them:
  - `running: Set<sessionId>` — every session's OWN execution state: the
    interpreter's `running` / `turnComplete` frames for ANY session id
    (children publish under their own id, `streamInterp.mjs:337-345`) and the
    connect-time `runningSet` replay;
  - `parentOf: Map<child, parent>` — `childSession` frames (`streamInterp.mjs:909-915`,
    `childParent`) plus delegate records (`childSessionID →
    displayParentID ?? parentSessionID`, from WS02's `delegateView.mjs`);
  - `jobs` — delegate records (`running`/`paused` count as work).
  Derivation (pure, `deriveWindowStatus(maps, sessionId)`):
  `busy` = `sessionsWithActiveWork(running, parentOf, jobs).has(sessionId)`
  (moved verbatim from `chatUtils.ts:2150`, any depth, cycle-safe, windowless
  descendants included); `subagents` = number of DIRECT children `c` with
  `parentOf.get(c) === sessionId` and `running.has(c)`; `startedAt` /
  `attention` from the interpreter state; `stopped` from the usage-stopped
  store.
  **Relationships are never inferred from tool status**, so a completed
  background-launch tool leaves `subagents`/`busy` up while its child runs.
  **Hydration** (startup and every opencode stream reconnect, next to
  `resyncAfterReconnect`, `index.mjs:3463`):
  - `running` ← `oc.listActiveSessionIds()` (`opencode.mjs:773`, a complete
    set — replaced, not merged; on failure the previous set is kept and the
    hydration is marked incomplete).
  - `parentOf` ← the **ancestry closure of every active session and every
    running delegate job's child**: for each such id, resolve its parent with
    NEW exported `oc.getSessionParent(id) → {status:"ok", parentID: string |
    null} | {status:"not-found"} | {status:"error"}` (wraps the private
    `getSessionInfo`, `opencode.mjs:873`, which today returns `null` for both
    404 and failures — the wrapper keeps them apart), then recurse on the
    parent until `parentID` is null or already known (cycle-safe, depth cap
    32). This is directory-independent and unbounded by listing pages (it does
    NOT use `listSessions(directory)`, whose 5-page / 500-session cap,
    `opencode.mjs:850-873`, and directory filter would miss ancestors). Edges
    from `childSession` frames and delegate records are merged in.
  - **Removal is only on authoritative evidence:** a session's parent never
    changes, so an edge is replaced only by an `ok` answer for that child and
    removed only on `not-found` for the child (the session was deleted) or a
    delegate record's removal (`delegate.updated`). `error` keeps the existing
    edge and marks hydration incomplete; an incomplete hydration retries with

## The transcript view on the box (D8–D11)

This is the largest unit. It is specified as one design and delivered in four
steps (turns → media → plan → activity/runs), each shippable alone.

### Where the box computes it

ONE pure module, NEW `src/server/transcriptView.mjs` (no I/O), used by three
call sites:

| Call site | When | What it annotates |
|---|---|---|
| `listMessages` (`opencode.mjs:511`) with `opts.view === true` | canonical fetch (open, refetch, load earlier) | the whole returned window |
| `getMessage` (`opencode.mjs:527`) with a third arg `{view: true}` | the desktop's live splice | one message (+ the interpreter's run ledger, D11) |
| `streamInterp.mjs` | live events | `toolRuns` frame (D11), `questions` (D10 via decorator) |

`opencode:message` gains an optional third arg `opts` (`{view?: boolean}`).

3. **Run boundaries — ONE classifier for canonical and live**

4. A `handoff` tool part ends the run and stands alone (both).
5. A non-blank reasoning part is transparent to the run but starts a new
   **segment** (what a "show reasoning" client draws as separate runs).
6. Parts are filtered as `visibleAssistantParts`; everything else that draws
   ends the run.
7. `clip` counts UTF-16 units (JS native).
8. **Execution boundaries do not end runs.** `session.execution.started` /
   `succeeded` are not boundaries in either path (the canonical walk never saw
   them); only rule 3–6 items are.

### Window edges (tail fetch, load earlier)

`listMessages` slices the window BEFORE today's annotation point

and annotates only the window. Consequences:
- a run that starts before the window keeps its TRUE id (its first part's id)
  and true `ownerMessageId` (outside the window), equal to the ledger's;
- clients draw such a run at the **first in-window message that has a part of
  it** ("placement message"); when "Load earlier" brings the owner in, the same
  row id moves up to the owner;
- a run that started more than `RUN_LOOKBACK` records before the window is
  annotated as if it started at the window (id = first in-window part) — logged
  once per fetch; accepted (requires >40 consecutive tool-only steps before a
  100-message tail).

### Run revisions

Every `RunView` carries `rev: {epoch, gen, seq}` (`RunRev`):
- `epoch` = the interpreter's process epoch (the `randomUUID()` minted at
  `createStreamInterpreter`, already used by the inbox K3 snapshot);
- `gen` = the session ledger's MEMBERSHIP generation: 1 when the ledger is
  created, incremented only by a canonical rebuild ("Provisional boundaries
  and canonical rebuild" below);
- `seq` = a per-session counter in the ledger, incremented on every change to
  ANY run of that session, stamped on the changed run (not reset by a rebuild).
- Every annotated part's `PartView` also carries `gen` (the generation its
  `runId`/`segmentId` were assigned under); canonical history the ledger does
  not know is stamped with the session's current `gen`.
- Canonical annotation: a run the ledger knows (same session, same id) is
  emitted with the LEDGER's current view and rev (so a full fetch can never
  regress live state); a run the ledger does not know (settled history) gets
  `rev: {epoch, gen: <current>, seq: 0}` and the canonical summary.
- **Authoritative epoch (no "epoch differs → wins").** The interpreter's
  epoch is announced on every `/events` connection: the connect snapshot's
  first frame, `runningSet` (always sent, index 0, `streamInterp.mjs:1062`),
  gains `epoch` (additive). Each client keeps `currentEpoch` = the epoch of
  the LATEST connection's `runningSet`, and a `connGen` counter incremented on
  every `/events` (re)connect.
  **Receiving path (WS11, wave D — not a WS02 deliverable):** `runningSet` is
  a top-level bus kind, NOT a `stream` sub (`streamInterp.mjs:1062-1069`), so:
  - server: `snapshotState()` puts `epoch` on the `runningSet` payload;
  - desktop: `RunningSetPayload` (`src/shared/types.ts:3011`) gains
    `epoch?: string`; NEW `src/renderer/runEpoch.ts` owns the per-connection
    state (`{epoch: string | null, connGen: number}`, a `store.ts` slice), fed
    by ONE App-level `window.api.onRunningSet` listener (`httpApi.ts:1159`)
    for the epoch and by `httpApi.ts`'s connection-transition handling
    (`:630-646`) for `connGen` (+1 on each transition to connected);
    `useTranscriptState.ts` reads `connGen` from the slice when it ISSUES
    `opencodeMessages` / `opencodeMessage` (`:178,221,268,287`) and passes it
    with the response into `mergeRunViews`; `useSseBus.ts`'s new `toolRuns`
    case reads `epoch` from the slice. A chat opened after the snapshot reads
    the already-stored slice (no per-chat subscription needed).
  - iOS: `StreamRunningSetPayload` (`MantaStreamModels.swift:204`) gains
    `epoch: String?`; `MantaEventStore` gains `@Published private(set) var
    connectionEpoch: String?` and `connGen: Int`, set in `applyRunningSet`
    (`MantaEventStore.swift:584`) and incremented on each transition to
    connected in its connection handling (`:568-587` area);
    `ChatSessionStore.refetch` captures `eventStore.connGen` before the request
    and passes `{epoch, connGen}` with the result to
    `TranscriptRunStore.merging`; `MantaStreamRouter`'s `toolRuns` case uses
    `connectionEpoch`.
- **Client merge rule** (one pure reducer per client — desktop
  `mergeRunViews(state, incoming, ctx)` in `toolActivity.ts`, iOS
  `TranscriptRunStore.merging(_:context:)` in `TranscriptViewModels.swift`):
  1. an incoming value whose `rev.epoch != currentEpoch` is REJECTED (a
     retired process's answer is never state); while `currentEpoch` is unknown
     (before the first `runningSet` of a connection) run writes are queued and
     applied after it arrives, through the same rule;
  2. an RPC response (canonical fetch or splice) carries the `connGen` it was
     ISSUED under; a response from an older `connGen` is discarded for the run
     map (it may still render text — the message content path is unchanged);
  3. within the current epoch, incoming wins iff `gen > stored.gen`, or
     `gen == stored.gen && seq >= stored.seq`; anything with `gen <
     minGen(session)` is rejected (`minGen` = the highest `gen` seen for that
     session in the current epoch);
  3a. **stale membership**: a message whose parts carry `gen < minGen` (e.g. a
     splice issued before a rebuild) is accepted for its CONTENT, but its
     `runId`/`segmentId` are ignored for layout and one canonical refetch is
     scheduled (desktop `scheduleRefetch()`; iOS `refetch()`), so a retired run
     id can never be resurrected by a late response;
  4. when `currentEpoch` changes (a new connection reports a different
     epoch), every stored run of another epoch is dropped, and the new
     connection's snapshot (`toolRuns` `full:true`) plus the next canonical
     refetch (clients refetch on reconnect today) repopulate it.
  The same rules apply to full snapshots and incremental frames: a `full:true`
  frame of the current epoch replaces the live layout/parts and merges runs by
  rule 3; a frame of another epoch is rejected like any value. A `rebuilt:true`
  frame (below) additionally DELETES every id in its `retired` list from the
  map, raises `minGen`, and schedules one canonical refetch.
- A canonical refetch after `turnComplete` does NOT clear the map; it merges
  (equal or newer revs). Runs no longer referenced by any loaded message and
  not in the current turn are pruned on refetch.

### Payload contract and guard

Default (D30): every message touching a run carries the FULL `RunView`; with
the rev rule, duplicates are harmless. Fallback, chosen by the guard below:
- the full `RunView` appears ONLY on the run's placement message in the
  response (owner if in window, else the first in-window message touching it);
  every other message touching it carries a `RunRef` `{id, rev, ref:true}`;
- a `RunRef` never overwrites a stored value (the reducer skips refs); a ref
  whose id has no stored value is an error case the box never produces within
  one response;
- `getMessage({view:true})` always returns FULL views for every run touching
  that one message (a splice must be self-contained).
**Guard** (`transcriptView.payload.test.mjs`, pass/fail, decides before D11
merges): serialize `listMessages({limit:100, slim:true, view:true})` vs
`{limit:100, slim:true}` over three synthetic fixtures — (a) a typical session
(the recorded fixture used by `opencode.test.mjs` for slim), (b) one 60-step
tool run with a reasoning segment every 2 tools, (c) the same widened to the
full history. If the default exceeds +30 % on (a) or (b), the implementation
switches to the `RunRef` fallback (same step) and the test then asserts the
fallback's bytes. Segment arrays are emitted only on the full view, never on a
ref.

### Wire contract — live (`toolRuns` frame)

The interpreter keeps a per-session **run ledger**, built with the same pure
functions as the canonical walk:
- **Lifetime:** the ledger is NOT reset at `session.execution.started` (rule
  8). It is reset when a DRAWING user message is delivered (rule 3) — the same
  point the canonical walk starts a new run — and on manta-server restart
  (new `epoch`). Closed runs older than the last drawing user message are
  dropped.
- **Parts** come from tool events (`ensureTool` / `finishTool`). Each ledger
  part keeps the descriptor-relevant canonical state INTERNALLY:
  `{type:"tool", id: tool.idx, callID, messageID, tool: name, state:{status,
  input: normalizeToolInput(v2Name, input), title: toolTitle(...),
  output: toolOutputText(v2Name, content) /* on success */, error /* on
  failure, errorFromV2 */}}` — the same fields `mapToolBlock` puts on the
  canonical part (`opencodeV2.mjs:199-216`), so wording (incl. the delegate
  name from output, rule 1) is computed identically. The output is held only
  while the run is in the ledger and is NEVER sent in the frame; raw disclosure
  data (output tail, diff) stays on the existing `toolOutput` frames / the
  canonical part, joined by part id / call id.
  `task` parts carry `childSessionId`; todo-write and handoff excluded as
  above.
- **Boundaries — classification data.** At `session.inbox.enqueued` time the
  interpreter records `deliveryClass.set(inboxID, deliveryClassOf(raw))` for
  EVERY enqueued item, where `deliveryClassOf` (in `transcriptView.mjs`)
  classifies by the item's MAPPED TRANSCRIPT OUTCOME, using the same mapper the
  canonical walk sees — never by `raw.type` alone (the pending-user filter in
  `inboxItemFromV2`, `streamInterp.mjs:95-119`, is a list-visibility rule, not
  a transcript rule):
  - `raw.type === "user"` → map with `mapTimeline([raw])`
    (`opencodeV2.mjs:422`), then `runBoundaryOf(message)`: `"draws"` or
    `"transparent"` (synthetic/ignored text, completion marker, blank → transparent);
  - `raw.type === "synthetic" && raw.metadata?.source === "subagent"` with
    the fields `mapBackgroundResult` needs (`opencodeV2.mjs:371`: `metadata`,
    `text`, `id`) → map it; a non-null result is an assistant message with a
    `background-result` part, which DRAWS → `"draws"` (rule 3); a null result
    (no child id to pair) → `"transparent"`;
  - any other synthetic / compaction / move item that `mapTimeline` drops →
    `"transparent"`;
  - an item lacking the fields its mapping needs, or of an unrecognised type →
    `"unknown"` (resolved by the buffered lookup below, never guessed here).
  Live placement of a visible background result: it is not a run, a text or a
  reasoning block, so the ledger records it only as a boundary; the iOS live
  tail does not draw it (it has no live frame today) and it appears with the
  canonical refetch at its own message, between run A and run B — the same
  position the canonical walk gives it. Handover therefore only ADDS that row;
  run ids A and B are already the canonical ones.
- **Boundaries — ordering.** `session.inbox.delivered` with a known class is
  applied synchronously (a `"draws"` closes the open run and resets the ledger
  per "Lifetime"). With an UNKNOWN class (enqueued before this process
  started, or missed), the ledger enters `pendingBoundary {inboxID,
  messageID}` and BUFFERS every later run-affecting event for that session
  (tool started/input/progress/success/failed, text and reasoning deltas,
  further deliveries) in arrival order — the same buffer-and-replay pattern
  the inbox hydration uses (`streamInterp.mjs:520-568`). Non-run frames
  (`toolStarted`, `toolOutput`, `flush`, …) are still emitted immediately; only
  ledger mutation and `toolRuns` frames wait. The injected async
  `classifyDelivered({sessionId, messageID})` (production: `oc.getMessage` →
  the canonical predicate over its parts, incl. `synthetic`/`ignored`)
  resolves the class; the boundary is applied FIRST, then the buffer is
  replayed in order, then ONE `toolRuns` frame is emitted. So a tool B that
  arrived during the lookup is assigned exactly as the canonical walk assigns
  it.
- **Failure / reconnect — provisional boundaries.** `classifyDelivered`
  failing, not resolving within 3 s, an opencode-stream reconnect while it is
  pending, or the 2 000-event buffer cap resolve the boundary as `"draws"`
  (logged) so the buffer is replayed — but the boundary is marked
  **provisional** (`ledger.provisional = {token, inboxID, messageID, fromSeq}`)
  and every run created or extended after it is "provisional range".
- **Provisional boundaries and canonical rebuild.** A provisional ledger is
  rebuilt from authoritative history — `rebuildFromCanonical(sid)` (injected;
  production: `oc.listMessages(sid, {limit: 100})` with the D11 lookback, then
  the canonical walk of `transcriptView.mjs` over the messages since the last
  drawing user message) — at the FIRST of: (a) the late lookup result arriving
  and DISAGREEING with the guess (an agreeing late result just clears the
  provisional mark), (b) the session's execution ending (`turnComplete`
  `complete:true`), (c) the reconnect resync. The rebuild:
  1. buffers run-affecting events that arrive during the read (same buffer);
  2. replaces the ledger's membership, layout and summaries with the
     canonical walk's, keeping ledger parts that canonical does not contain yet
     (unsettled messages), attached by the same rules;
  3. increments `gen`, stamps every run with the new `gen` and a fresh `seq`,
     and computes `retired` = ledger run ids that no longer exist (e.g. B when
     the true boundary was transparent and B belongs to A);
  4. replays the buffered events, then emits ONE `toolRuns` frame with
     `full:true, rebuilt:true, gen, retired`;
  5. invalidates the provisional token: a lookup result for that token that
     arrives later is ignored (stale), and a second rebuild for the same token
     cannot start.
  After a rebuild, `getMessage({view:true})` stamps from the rebuilt ledger
  (new `gen`), so a later splice or tool update cannot restore the guessed
  split; client rule 3/3a reject anything older.
- **Text / reasoning boundaries:** a `session.text.delta` chunk containing
  non-whitespace closes the open run (rule 6); a non-whitespace
  `session.reasoning.delta` starts a segment (rule 5).
- **Ordered layout:** the ledger also records the turn's draw order as it
  happens — `layout: LiveBlock[]`:
  ```ts
  type LiveBlock =
    | { kind: "run", id: string, segmentId: string }    // ONE entry per SEGMENT of a run (segmentId of the
                                                        // first segment === run id; a run without segments
                                                        // has exactly one entry with segmentId === id)
    | { kind: "text", partID: string, messageID: string }     // the `flush` partID, e.g. "<msg>:text:0"
    | { kind: "reasoning", partID: string, messageID: string }
  ```
  A text/reasoning block is appended when its partID's FIRST non-whitespace
  chunk arrives; a run entry when the run opens AND when a new segment of it
  starts (the first part after a non-blank reasoning). Tool A → reasoning R →
  tool B yields `[run(A, seg A), reasoning R, run(A, seg B)]`.
  **Placement rule (both clients, canonical and live — one rule, KC layout):**
  - reasoning SHOWN: every run entry draws its own block — the segment's
    `SegmentView` summary, row id `"run-" + segmentId` — and reasoning entries
    draw between them: segment A, R, segment B;
  - reasoning HIDDEN: reasoning entries draw nothing, and consecutive run
    entries with the SAME run id (nothing drawn between them) collapse into ONE
    block at the FIRST entry, drawing the whole `RunView`, row id `"run-" + id`.
    Since the first segment id equals the run id, toggling keeps the first
    row's id; segment rows appear/disappear after it.
  The canonical layout uses the same rule: parts carry `segmentId`, so the
  canonical walk emits one entry per (run, segment) in part order, with
  reasoning parts between them. `partID`s are exactly the
  `flush` frame ids (`streamInterp.mjs:818`) and the canonical part ids
  (`opencodeV2.mjs:254-270`).

Frame (`{kind:"stream", sub:"toolRuns", sessionId, payload}`):

```ts
{ epoch: string, full: boolean, gen: number,
  rebuilt?: true, retired?: string[],      // only on a canonical rebuild (see above)
  layout: LiveBlock[],                     // the whole ordered layout of the ledger (small: one entry per block)
  runs: RunView[],                         // runs that changed since the last frame (all when full)
  closed: string[],                        // run ids that closed since the last frame (all closed when full)
  parts: { id: string, callID: string, messageID: string, runId: string, segmentId?: string,
           tool: string, status: string, childSessionId?: string, activity: ActivityView }[] }
```

`closed` makes "is the last run still open?" explicit even when a close does
not change the summary. Emitted coalesced (≤ 1 per 100 ms per session, reusing
the `messageChanged` timer seam) on tool start / input known / end, run close,
segment break, text/reasoning block start, and a final frame at execution end;
`full:true` in the connect snapshot for every session with a non-empty ledger
(`snapshotState()`). `getMessage({view:true})` stamps `runId`/`segmentId` from
the ledger for parts the ledger knows and attaches the ledger's `RunView`s
(with revs); parts it does not know (history) are annotated within the message
alone with `seq: 0`.
