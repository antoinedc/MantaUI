# WS11 — Server consolidation

Status: draft · Date: 2026-10-28 · Branch: `feat/ios-desktop-parity` · Wave: **D** (runs alone, after C-int)

## Goal

D23 makes the box the only owner of logic. Waves A–C ported desktop logic into
Swift (WS01, WS03, WS04, WS08, WS10, plus older ports). WS11 moves every
MOVE-NOW item that `server-first-audit.md` §3b assigns to WS11 onto the box,
switches the **desktop** to the box result and deletes the desktop copy, then
switches **iOS** and deletes the Swift port. No parallel implementations, no
parity fixtures, no "fallback for old boxes" (D24).

Items in scope (audit IDs): **U1** T1, T2, T4, T5, T8, T16 · **U2** S1, S2, S3,
S8, S10, S13, S14 · **U3** T20, T21, X1, X3, X5, X6, X9 · **U4** K2, K3, K5, K7 ·
**U5** capabilities + guardrails. Every MOVE-LATER item is listed in
[Follow-ups](#follow-ups-move-later-tickets).

Because WS11 runs alone it may edit any file (server, desktop renderer, iOS app,
`Package.swift`, `project.yml`). It still follows ground rules 1–5 and C1–C7.
`MantaUI.xcodeproj/project.pbxproj` is regenerated by the orchestrator at the
end (D18), never by the worker.

## Ground rules specific to WS11

1. **One module per family, node-tested.** Each sub-step adds its own server
   module + `*.test.mjs`. Channel registration in `src/server/rpc.mjs`, routes
   in `src/server/index.mjs` and edits to `src/server/streamInterp.mjs` are done
   by the worker (sole worker in wave D, D24).
2. **Additive wire only (K2).** New channels, new response/frame fields, opt-in
   request flags. No existing field changes meaning. An old desktop on a new box
   keeps working unchanged.
3. **Capability-gated clients (D24).** Every moved surface checks one box
   capability id (D1). Missing → the surface follows the no-dead-control rule
   (hidden, or disabled with **"Update your box to use this"**). No copy of the
   old client logic is kept for old boxes.
4. **Box text uses the desktop wording** unless this spec names a change. Where
   desktop and iOS disagreed, the chosen rule is stated and called out under
   [Behaviour changes](#behaviour-changes-to-call-out-in-the-pr).
5. **Time-relative text keeps a box instant** and the client compares it to its
   own clock (T21 `staleAt`). Exception, accepted by the audit: K3 health lines
   are worded at response time (they are polled).
6. **Sub-steps are independent.** Each D-n is implemented, reviewed and merged
   into the branch on its own, in order. A later step never edits a module an
   earlier step finished except to register its capability id.

## D1 — Capabilities list + guardrails (U5)

### State at the start of wave D (built in wave B/C)

The capability list already exists (master D25, WS02 SF-0):
`src/server/boxCapabilities.mjs` exports `BOX_CAPABILITIES`; `GET /api/version`
(`writeVersionResponse`, `version.mjs`) and `server:version` (`rpc.mjs`, M-02-srv-1)
return it as `capabilities: string[]`. It carries every id in the master's
"Capability id registry" (wave B: 02/07/09/06; wave C: 05). The single client
accessors are WS02's iOS `MantaAPIClient.boxCapabilities() -> Set<String>`
(+ the chat-scoped `ChatCardCapabilities` store) and desktop
`src/renderer/hooks/useBoxCapabilities.ts` → `useBoxCapability(id)`.
Specs 05/06/07/09 detect old boxes by an exact response-shape / unknown-channel
signal; their ids are registered but not all read.

### Wire contract

- No new module and no rename: D1 EXTENDS `src/server/boxCapabilities.mjs`
  (the name already differs from `src/server/capabilities.mjs`, the plugin
  capability-job queue). Each later sub-step appends its id(s) to
  `BOX_CAPABILITIES`. `version.mjs` / `rpc.mjs` already return the list — no
  edit needed beyond what each sub-step registers.
- Both paths are upgrade-exempt already (`/api/version`), so the list is
  readable while the box upgrades.
- Ids are lowercase `kebab-name-N` (`/^[a-z0-9-]+-\d+$/`, the master registry
  format); an id is never reused for a different shape. A shape change ships a
  new id (`…-2`) and keeps the old one until clients drop it.

### Client behaviour (both clients)

- The list is fetched once per connection (on connect and on every reconnect),
  alongside the existing version read. Unknown ids are ignored.
- **Missing capability → the dependent surface is hidden, or rendered disabled
  with the static note "Update your box to use this"** (and, on iOS, a "Box
  updates" link to `MantaRoute.settings(section: "updates")`). The table per
  sub-step lists which. A surface is never left as a control that does nothing.
- While the list is unknown (first connect in flight) surfaces render their
  loading state, not the "update" note.

### Wire contract

**`cache` frame** (`{kind:"stream", sub:"cache", sessionId, payload}`), payload
gains two fields:

```ts
{ isStale: boolean, idleMs: number, staleTokens: number, ttlMs: number,   // unchanged
  lastCompleted: number | null,   // NEW epoch ms of the last finished step
  staleAt: number | null }        // NEW epoch ms when the cache goes cold; null = never (not eligible)
```

`staleAt = lastCompleted + ttlMs` when `!running && lastCompleted != null &&
staleTokens >= STALE_CACHE_MIN_TOKENS`, else `null`. New pure
`computeStaleAt({lastCompleted, ttlMs, cachedTokens, running, minCacheTokens?})`
in `src/shared/streamInterpretation.mjs` (box-run; `computeStaleCache` keeps
its current output and now also returns `lastCompleted`/`staleAt`).

Emission changes in `streamInterp.mjs`:
- keep the step-end emit;
- **NEW** emit at the running→false edge (`emitRunning(sid, st, false)` and
  `emitTurnComplete` with `complete:true`) — this is the emit that carries a
  non-null `staleAt`;
- **NEW** replay in `snapshotState()` for every session with `lastCompleted`;
- **NEW** `setCacheTtlLabel(label)` on the interpreter, called from the
  `config:update` handler in `rpc.mjs` when `cacheTtl` changes (today the label
  is read once at boot, `streamInterp.mjs:223-231`), re-emitting `cache` for
  known sessions.

**NEW channel `opencode:cache`** — `args: [sessionId]` → the same payload
computed from the persisted transcript (last assistant `time.completed`, its
`tokens.cache.read + write`, the configured TTL, `running` from the interpreter),
or `null` when no assistant turn has completed. Mirrors `opencode:context`
(`rpc.mjs:1322`). Never throws for a valid id; unknown session → `null`.

**`context` frame + `opencode:context`**: computed against the **selected**
model. NEW `src/server/sessionContext.mjs`:

```js
// resolution order: model-prefs session record → config.defaultModel → last-used (st.model / transcript)
export function contextModelFor({ sessionId, prefs, config, lastUsed }) → { providerID, modelID, basis: "selected" | "default" | "last-used" } | null
```

Payload gains (additive): `limit: number | null`, `model: {providerID, modelID} | null`,
`basis: "selected" | "default" | "last-used"`. The interpreter keeps the last
step's tokens per session (`st.lastStepTokens`) and exposes
`reemitContext(sid)`; `model-prefs:set` (`rpc.mjs:2418`) calls it after a write
for that session, and `config:update` calls it for all known sessions when
`defaultModel` changes. Prefs are read through `modelPrefs.mjs`
`getModelPrefs()`, cached in memory and invalidated by `model-prefs:set`/`seed`.

## The transcript view on the box (D8–D11)

This is the largest unit. It is specified as one design and delivered in four
steps (turns → media → plan → activity/runs), each shippable alone.

### Where the box computes it

ONE pure module, NEW `src/server/transcriptView.mjs` (no I/O), used by three
call sites:

| Call site | When | What it annotates |
|---|---|---|
| `listMessages` (`opencode.mjs:511`) with `opts.view === true` | canonical fetch (open, refetch, load earlier) | the whole returned window |
| `getMessage` (`opencode.mjs:527`) with a third arg `{view: true}` | the desktop's live splice | one message (+ the interpreter's turn ledger, D11) |
| `streamInterp.mjs` | live events | `toolRuns` frame (D11), `questions` (D10 via decorator) |

`opencode:messages` passes `opts` through already (`rpc.mjs:1314`);
`opencode:message` gains an optional third arg `opts` (`{view?: boolean}`).
The annotation runs on the FULL mapped messages **before** `slimTranscript`
(so reasoning boundaries are known even when slim drops reasoning parts) and
after `stampCommandOrigins`. Without `view:true` the output is byte-identical to
today (old desktop, K2).

### Response shape (additive)

The response is still `OpencodeMessage[]`. With `view:true`:

```ts
type OpencodeMessageWithView = {
  info, parts,                       // unchanged; tool/patch/file parts may gain `view` (below)
  view?: MessageView                 // NEW, absent when empty
}
type MessageView = {
  turn?: TurnView,                   // D8 — only on the last assistant message of a finished turn
  truncation?: TruncationView,       // D8 — any assistant message with a classified finish
  media?: MediaView[],               // D9 — canonical media this message owns
  runs?: RunView[]                   // D11 — every run that has a part in this message
}
```

Payload impact (measured target, verified in review on a real session): turn +
truncation ≈ 80 B per turn; media ≈ 150 B per entry; runs/activity ≈ 150 B per
tool part + ≈ 250 B per run per message it touches. For the iOS tail fetch
(slim, 100 messages) this is expected to add 10–25% back, about what slim
removed. If review measures more than +30%, `RunView` repeats on absorbed
messages are dropped to `{id}` references (open question 3).

### Correctness while streaming

- **iOS** does not refetch mid-turn (it refetches on `running` start and on
  `turnComplete`, `ChatSessionStore.swift:689-690`), so its live turn comes from
  frames only: `toolRuns` (D11), `media` (existing), `truncation` (existing).
  At `turnComplete` the canonical refetch replaces live data; ids are equal, so
  rows keep identity.
- **Desktop** splices one message per `messageChanged` (`useTranscriptState.ts:189`).
  Spliced messages carry part `view.activity` and `view.runs` from the
  interpreter's **turn ledger** (D11), so the summary of a run that started in an
  earlier message is updated by the newest message that touches it (rule: for a
  run id, the copy on the LATEST message in transcript order wins). Turn footers
  need the whole turn, so they arrive with the canonical refetch the desktop now
  schedules when `running` settles to false (NEW `scheduleRefetch()` in the
  `turnComplete` settle timer, `useSseBus.ts:575-593`).
- No client ever computes wording, run membership, summaries or footers.

### iOS row identity (mobile/native/AGENTS.md §6) — preserved

- Run rows keep `id = first part id` (`ToolRun.id`), segment rows `id = segment's
  first part id` (the first segment shares the run id). The box derives both
  from part ids, and `TranscriptRow`'s `stableScrollID`/`uniqueTranscriptRows`
  are unchanged.
- Media rows keep `TranscriptMediaIdentity` ids (`media:h:<handle>` /
  `media:s:<messageID>:<path>`); the box emits exactly these strings.
- Footer rows keep `messageID`.
- Nothing about row ORDER changes: the client still places blocks by walking
  messages in order; the box only says what each block contains.
- Toggling "show reasoning" swaps a run row for its segment rows; ids remain
  deterministic. That toggle already re-renders the list (D22 refetch).

### Wave-B call sites that consume WS01 mapper entry points (checked)

### Wire contract — canonical

```ts
type ActivityView = { kind: ActivityKind, status: "pending" | "running" | "completed" | "error",
  label: string,          // the label for the current status
  target: string,         // full path / command / pattern / url, "" when none (ToolActivity.target)
  counted: boolean }      // false for patch parts
type PartView = { activity?: ActivityView, runId?: string, segmentId?: string,
  media?: { kind: "image" | "video", path: string } }        // D9
type RunSummary = { label: string, calls: number, failed: number,
  tone: "ok" | "warn" | "running",
  live: { kind: ActivityKind, label: string } | null }      // latest unfinished tool, present tense
type RunView = RunSummary & { id: string, ownerMessageId: string,
  segments?: (RunSummary & { id: string })[] }             // only when rule 5 split it
```

- Every tool/patch part in a run gets `part.view.activity` + `runId` (+
  `segmentId` when the run has segments). A handoff or todo-write part gets no
  `runId`.
- Every message with at least one run part carries `view.runs` = the runs those
  parts belong to (full summary of the run as of this response). A run is drawn
  once, at `ownerMessageId`.
- Payload: `partIds` are deliberately absent (parts carry `runId`).

### Wire contract — live (`toolRuns` frame)

The interpreter keeps a per-session **turn ledger** (reset on
`session.execution.started`), built with the same pure functions:
- parts from tool events (`ensureTool` / `finishTool`), each a synthetic part
  `{type:"tool", id: tool.idx, callID, messageID, tool: name, state:{status,
  input: normalizeToolInput(v2Name, input), title: toolTitle(...)}}` — the same
  inputs `mapToolBlock` gives the canonical part, so wording matches;
  `task` parts carry `childSessionId`; todo-write and handoff excluded as above;
- run closers: a `session.text.delta` chunk containing non-whitespace,
  `session.inbox.delivered` (a steered user message), a `file` part;
- segment breaks: a `session.reasoning.delta` chunk containing non-whitespace.

Frame (`{kind:"stream", sub:"toolRuns", sessionId, payload}`):

```ts
{ turnStartedAt: number | null, full: boolean,
  runs: RunView[],                         // runs that changed since the last frame (all when full)
  parts: { id: string, callID: string, messageID: string, runId: string, segmentId?: string,
           tool: string, status: string, childSessionId?: string, activity: ActivityView }[] }
```

Emitted coalesced (≤ 1 per 100 ms per session, reusing the `messageChanged`
timer seam) on tool start / input known / end, run close, segment break, and a
final frame at execution end; `full:true` in the connect snapshot for running
sessions. `getMessage({view:true})` stamps `runId`/`segmentId` from the ledger
for parts the ledger knows and attaches the ledger's `RunView`s; parts it does
not know (history) are annotated within the message alone.

   touches (latest-wins)**, with a size guard: if review measures the iOS slim
   tail payload (100 messages) growing by more than 30 %, `RunView` repeats on
   absorbed messages are dropped to `{id}` references in the same step.
4. **Context basis with no explicit selection — last reply's model, labelled.**
   With no model-prefs record and no `defaultModel`, the box uses the last-used
   model and sends `basis:"last-used"`; both clients label the context sheet
   "(last reply's model)".
5. **Seat-move copy — box-owned text for both surfaces.** The box ships the iOS
   notice sentence (`text`) and the desktop dial line (`line`); both surfaces
   stay, neither client composes the words.
