1. **BLOCKING — F12 / Client members / wave prerequisite / Contracts.** WS10 still says it consumes WS04's `launchers()`, `SessionLauncher`, and `SessionLauncherFlags.resolve`, and explicitly refuses to provide launcher discovery itself. Binding D20–D21 and revised WS04 instead require WS10 to provide `launchersList()`, `AvailableLauncher`, and `ExtensionsLaunchers.resolve` in A1, before WS04 runs in A2. Following the two implementation briefs produces neither provider and leaves both consumers uncompilable; the header also creates a backwards prerequisite on A2. **Evidence:** `10-settings-box.md:3-5,435-439,927-956,1197-1201`; `04-sessions.md:159-163,1295-1296,1353-1354`; `00-master.md` D20–D21. **Fix:** restore WS10 ownership of the canonical launcher member, wire types (including flag type), and resolver; pin their full signatures in the client/provider table, add resolver tests, and remove every WS04-launcher prerequisite/reference including review response X6. WS04 must consume precisely those symbols, with no second reader/resolver.

2. **BLOCKING — M-10-1 versus WS04's Mounts applied.** WS10's revised Foundation-only theme API is `SettingsAppearance.preference(for:) -> ThemePreference`, with `.colorScheme` supplied in a separate SwiftUI extension. WS04's mount still calls the removed `SettingsAppearance.colorScheme(for:)`. Applying that ledger literally cannot compile. **Evidence:** `10-settings-box.md:176-191,1172`; `04-sessions.md:1323` (M1). **Fix:** synchronize WS04's mount to `.preferredColorScheme(SettingsAppearance.preference(for: themePref).colorScheme)` and require both provider files from A1. Use the canonical IDs M-10-1/M-10-2 in the receiving ledger and the D20 A2 applier; remove the obsolete same-wave/rebase fallback wording.

3. **SHOULD — §0.2 reset/undo interaction.** The new statement that writes are serialized and `values` contains only confirmed values excludes reset/undo, which still mutate `values` and issue independent writes. Only the individual row is disabled during commit. A user can toggle a worktree setting, tap Reset while that request is pending, and receive the two completions in either order; the commit can overwrite the reset's local value while the box ends with the reset value. This defeats the newly promised failure-safe display. **Evidence:** `10-settings-box.md:92-115`; `mobile/native/MantaUI/MantaSettingsStore.swift:157-224` independently implements reset/undo; `SettingsScreen.swift:221,426,457` exposes those actions. **Fix:** at minimum disable reset/undo while commits are saving and block commits while a reset/undo write is in flight, with a shared mutation guard. Add a gated-store interleaving test. This need not redesign the explicitly deferred optimistic reset behavior.

4. **SHOULD — F18 classifier / F14 server-address accessor.** Two newly specified calls name members that do not exist: `UpgradePresentation.isUpgradeRefusal(503, body)` and `KeychainCredentialStore.shared.serverUrl`. The actual refusal helper belongs to `UpgradeStatus` and has argument labels; the Keychain store exposes `serverURL: URL?`, while `serverUrl: String` belongs to loaded credentials. **Evidence:** `10-settings-box.md:505,687`; `mobile/native/MantaUI/UpgradeModels.swift:381-391`; `KeychainCredentialStore.swift:5,21`. **Fix:** cite `UpgradeStatus.isUpgradeRefusal(statusCode: 503, body: body)` and use `KeychainCredentialStore.shared.serverURL?.absoluteString` (or explicitly load the credentials). Keep `RawRPCResponse` with the Foundation-only models so the package classifier does not depend on the app-only HTTP client.

5. **SHOULD — C2 Settings deep-link contract / mount ledger.** The revision retains the `initialSection` initializer promise but drops the original instruction to scroll to that section. Merely adding an unused parameter compiles yet makes `.settings(section:)` land at the top regardless of its destination. The mount IDs are also inconsistent: WS10 now uses M-10-3 for Package.swift, while WS04 calls its Settings presentation M-10-3/M3; WS10 lists WS09's current M-09-1 as M1. **Evidence:** `10-settings-box.md:1174-1187,1202-1205`; `04-sessions.md:1111,1325`; `09-models-usage.md:1227`; existing `mobile/native/MantaUI/SettingsScreen.swift:35-76,156-164` has neither the parameter nor scrolling behavior. **Fix:** restore a concrete section-id/ScrollViewReader behavior (after content is available, nil/unknown IDs safely use the top), test a non-first section, and reconcile the three ledger IDs without assigning Package.swift and Settings presentation the same ID.
