# WS09 review — round2

Round-1 disposition: **#1, #2, #3, #4, #5, #7 and #8 are materially resolved** by the explicit partial-save outcome, disarm-only Apply, all-path selection policy, awaited opt-in, refreshed eligibility result, connection subscription/seed ordering, and expired-reset guards. **#6 is only partially resolved**: generation checks and reset mounts now exist, but client rebinding is missing (finding 1). No rebuttal needs rejecting. D16/D17 correctly remove the duplicate stopped-state owner and seat helper. The client-member inventory has no duplicate names in the other revised specs. Outstanding integration discrepancies follow.

1. **BLOCKING — Box lifecycle / F1 catalogue / F7 store. Resetting state does not rebind the client to the new box.** The new lifecycle clears data and advances a generation, but never specifies replacing the singleton's API client. The existing catalogue holds `private let api`, initialized once with `.live()`. That client's URL is fixed at construction, while its default token provider reads the current Keychain token for every request. After switching from box A to B, a new-generation reload can therefore send B's bearer token to A and then accept A's response as current. An early singleton initialization before first pairing can also retain the loopback placeholder URL. **Evidence:** `mobile/native/MantaUI/ChatModelCatalog.swift:30-37`; `mobile/native/MantaUI/MantaAPIClient.swift:3-21,985`; WS09 “Box lifecycle” and M-09-4 specify data reset only. **Fix:** pin an explicit per-box client lifecycle for both singleton stores: construct/rebind the client from the new paired URL and its matching credential before issuing any new-generation request, and invalidate the old client on removal/switch. Bind URL and token to the same box identity, rather than combining a retained URL with a dynamically changing token. Add tests for unpaired→paired and A→B, asserting the actual request host and authorization pairing as well as rejection of late responses. This belongs in WS09-owned stores/factories; request any non-owned mount explicitly.

2. **BLOCKING — F6 Wire contract / Cross-spec dependencies: stoppedLastLooked type disagrees with its owner.** WS09 consumes and requests `SessionListStore.stoppedLastLooked: Double?`, but WS04 explicitly provides `Date?`. The sheet cannot pass the latter directly into the epoch-millisecond logic described here; treating seconds as milliseconds would also make all “new” comparisons wrong. This is no longer a missing optional dependency: the provider has committed to a different type. **Evidence:** `09-models-usage.md:876,1264-1269`; `04-sessions.md:1345-1350`; the wire store returns its numeric `lastLooked` at `src/server/stoppedStore.mjs:274-289`. **Fix:** consume WS04's `Date?` and convert at the sheet boundary with `timeIntervalSince1970 * 1000` for WS09's pure epoch-ms inputs (or jointly pin one different type in both specs). Remove the stale claim that WS04 has not provided this member. Pin units for the stopped-entry mapping too. Test nil and equal/before/after timestamps through the boundary conversion.

3. **BLOCKING — Files / D19 manifest: the pure resume module's input type is placed in an excluded SwiftUI file.** F6 requires every `UsageResume` helper to use `UsageStoppedEntry`, but the Files table puts that struct in `UsageResumeSheet.swift`, marks that file non-Foundation, and includes only `UsageResumeLogic.swift` in the package. Following the manifest leaves the Linux target with an undefined type. **Evidence:** `09-models-usage.md:900-905,942-953,1170`; `mobile/native/Package.swift:37-59` uses an explicit source list, and its header explains that SwiftUI files cannot be included. **Fix:** define the Foundation-only `UsageStoppedEntry` struct in `UsageResumeLogic.swift` (or an explicitly included Foundation file). Put only `extension UsageStoppedEntry { init(_ record: SessionStoppedRecord) … }` and `UsageStoppedCapsule` in the sheet file. Correct the manifest and require the integrated `verify.sh` run to compile the resume tests.

4. **SHOULD — Mounts applied / counterpart mount IDs: the claimed cross-check is stale.** WS09 says no request targets an owned file and calls the provider-change observer “not a mount.” WS08 now explicitly requires **M-08-1** in `ChatModelCatalog.swift`, applied by WS09, including a notification-triggered reload test. F1 includes the observer behavior, so this is not a missing runtime feature, but the ledger and required test do not agree. WS02 also still calls the active-session mount “M4”, while WS09 now names it M-09-5; its behavior matches. **Evidence:** `09-models-usage.md:1237-1245` and its ModelsStoreTests list; `08-accounts.md:995` (mandatory mount and exact test); `02-chat-cards-queue.md:801`; WS09 M-09-5. **Fix:** record M-08-1 under Mounts applied with its provider symbol, notification observer and reload test; align WS02's receiving row to M-09-5 (with a legacy alias if needed). The M-09-1 through M-09-4 integration-agent assignments otherwise conform to D18, and the optional Accounts link remains explicitly optional.

5. **SHOULD — F4 declareOutcome: an unsupported refresh can still be mistaken for success.** The revised outcome correctly keeps identity-only rows, but it accepts only `[UnidentifiedRow]?` and treats absence of the key as proof that Auto can describe it. The same new endpoint explicitly returns `{supported:false, rows:[]}` when the catalogue is unavailable. Dropping that envelope flag makes an unsupported refresh indistinguishable from an eligible endpoint and shows a false “Auto can now describe …” confirmation. **Evidence:** WS09 F4 “Wire contract” empty-catalogue result, “Save / Confirm / candidate pick” outcome rules and `declareOutcome(key:, refreshed: [UnidentifiedRow]?)`; `src/server/modelCatalog.mjs:18-24` documents unsupported catalogue state. **Fix:** pass the full `UnidentifiedList` (including `supported`) into the outcome helper. Only a supported refresh with the key absent proves resolution; unsupported should preserve the saved-write confirmation while showing the catalogue-unavailable state. Add a successful-write→unsupported-refresh case beside the existing refresh-failure test.
