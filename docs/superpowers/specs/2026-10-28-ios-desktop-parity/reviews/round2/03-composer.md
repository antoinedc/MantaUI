# WS03 review — round2

Round-1 verification: findings 1, 2, 3, 4, 5, 7 and 8 are addressed in WS03: the duplicate draft declaration is removed; adoption belongs to WS03; accepted command cleanup is ID-based; Clear confirms; submission is guarded before lookup; D6/D10 are respected; list RPCs use `callRequired`. Finding 6 has a valid proposed fix but its receiving workstream has not accepted it (finding 1 below). The new fork use of the settle helper is a separate regression, not a failure of the command cleanup fix.

1. **BLOCKING — Mount requests M-03-5/6/7; receiver receipts.** The required agent-error members and read-only controller wiring have no matching receiver deliverables. WS09 explicitly says it applies no mounts and does not change the agents member. Implementing integration mount M-03-6 against that result references nonexistent `agentsLoadError` and `retryAgents()`. WS02 likewise does not receipt M-03-7, leaving `acceptsInput` true on background-job screens; WS05 then exposes fill actions for a composer that is hidden. **Evidence:** `03-composer.md:597-599`; `09-models-usage.md:1237-1245`; `02-chat-cards-queue.md:785-807`; `05-git-pr-review.md:263-273`. Existing `mobile/native/MantaUI/ChatModelStore.swift:136-143` has neither new member and permanently folds errors into `[]`. **Fix:** reconcile both receiving specs: WS09 must explicitly accept M-03-5 with the pinned members and tests; WS02 must accept M-03-7, initialize the controller's writability and keep it synchronized with ownership changes. Keep M-03-6 gated on those members landing. Add an integration acceptance check for retry and for a job screen opened directly/reclassified after opening.

2. **BLOCKING — F6/F7, M-03-4, Mounts applied; WS04 draft consumption.** The specs prescribe incompatible new-chat seed entry points. WS03 claims WS04 passes `draft:` into the wave-A adoption, but WS04 actually passes `initialCarryOver:` and delegates creation of that parameter to WS02 in wave B. WS02's receipt still names a third interface, `seedAttachments`. Following the per-wave instructions leaves WS04's wave-A call uncompilable until an unreceipted later mount, bypasses WS03's `attach` validation, and leaves duplicate seeding paths available. **Evidence:** `03-composer.md:550-555,596,607`; `04-sessions.md:1174-1184,1317`; `02-chat-cards-queue.md:798`. Current `mobile/native/MantaUI/ChatScreen.swift:297-309` directly seeds chips from carry-over rather than validating them via `attach`. D11 requires the reverse mapping through `attach`. **Fix:** choose one end-to-end contract and update all three specs and ledgers. The already-provided wave-A `ChatScreen(draft:)` is sufficient: have WS04 pass the canonical draft to it, retire M-04-7/`initialCarryOver` and the stale `seedAttachments` receipt for this flow, and retain existing handoff carry-over only for handoffs. Test one-time text/chip seeding, rejection feedback, and no reseeding after clear/handoff.

3. **BLOCKING — F2 step 4, built-in Fork cleanup.** The revision calls the accepted-submission settle helper immediately after `onSlashFork?()`. That helper removes every snapshotted ready chip, but Fork has not sent or carried any of those attachments, and the callback does not even report whether the asynchronous fork succeeded. Thus typing `/fork` with ready attachments deletes them from the original draft even when the fork fails. **Evidence:** `03-composer.md:269-270` versus its settle contract in F2; `mobile/native/MantaUI/ChatScreen.swift:570` starts a Task through a Void callback; `:968-993` forks the session with only an optional text seed and reports failures independently. **Fix:** do not use message-acceptance cleanup for local built-ins. Preserve attachments and agent selections for Fork; at most consume the command text according to an explicit local-action policy. If cleanup is intended to depend on success, pin an awaited success-returning callback and its owner mount. Add a test covering `/fork` plus a ready attachment with both success and failure.

4. **SHOULD — F2 snapshot and post-lookup dispatch.** The revision correctly snapshots the user's payload, but also freezes `store.running` before the potentially three-second lookup and uses that stale value to choose delivery/model synchronization. A turn starting during lookup can receive a command without delivery, with model/agent synchronization enabled; a turn ending during lookup can cause a now-idle action to be refused. **Evidence:** `03-composer.md:257-273`; `src/server/opencode.mjs:2987-2992` distinguishes control synchronization solely by presence of delivery. The current prompt dispatcher checks running at dispatch (`mobile/native/MantaUI/ChatSessionStore.swift:1276-1290`). **Fix:** retain immutable text/chips/model preference snapshots but re-read live running/ownership state immediately before choosing the command dispatch branch or executing a local built-in. Keep the user's chosen Now/After-this-turn delivery preference. Add acceptance cases for idle→running and running→idle during command loading.

Client-member check: `commands`, `references`, and `runCommand` have no duplicate declarations in the other specs; WS10 correctly consumes WS03's `references()`/`OpencodeReferenceInfo` in its references section. M-03-1…4 are consistent with D13 ownership; M-03-8 follows D18/D19. The outstanding cross-spec problems are the receiver receipts and seed interface above. WS03's claim that WS02 still uses a legacy composer fallback is stale: WS02 now explicitly consumes the adopted controller (`02-chat-cards-queue.md:49-50`).
