## Findings

1. **BLOCKING — F11 / Mounts applied, WS01 integration remains incompatible.** The receipt table still uses `TranscriptMediaStore.shared.entries[sessionId]` and `$entries`, whereas revised WS01 exposes `entries(for:) -> [TranscriptMediaEntry]` and `$sessions`. Its mapper now takes an array for `liveMedia`, not a dictionary. These calls will not compile. The same receipt suppresses truncation solely because the message is loaded, while WS01 now requires proof that a footer actually displays that truncation; WS02 also explicitly drops the live truncation map that WS01's revised fallback requests. This can remove the only truncation warning. **Evidence:** WS02 `02-chat-cards-queue.md:793–797`; WS01 `01-transcript.md:322–324`, `:1216–1227`, `:1371–1374` (M-01-1 through M-01-4). **Concrete fix:** replace the old M3a–M3e receipts with the current M-01-1–4 signatures, including `liveMediaTail(messages:live:)`, `$sessions`, and remapping on command changes. Adopt `footerTruncationMessageIDs(liveTranscript)` for notice suppression. Resolve the live-truncation amendment explicitly with WS01/master D15: either supply its bounded fallback map, or remove WS01's dependency and retain the standalone notice when canonical data cannot produce a footer. Do not leave both contradictory contracts. Test a loaded message with no canonical truncation metadata and a live truncation frame.

2. **BLOCKING — F6 / Mounts applied, remaining provider signatures and draft transport are stale.** The integration table cannot be implemented against the current provider specs as written:
   - WS06 exports `SearchScope.fromProjects`, not `SearchScope.build` (WS02 `:799`; WS06 `06-search.md:568`).
   - WS07's artifact mount accepts `composer:`, not `onAttach:` (WS02 `:800`; WS07 `07-artifacts-cards.md:860`).
   - WS04's new-session transport is `initialCarryOver`, not `seedAttachments`; without M-04-7 the destination initializer cannot compile and the carried attachments do not reach the composer (WS02 `:798`; WS04 `04-sessions.md:1317`).
   - F6 calls `navigator.windowKey(...)`, but WS04 declares a **static** `MantaNavigator.windowKey(...)` (`04-sessions.md:1088`). Swift does not call a static member through an instance.
   - WS04's mode mount now requires `AvailableLauncher`, `launcherCatalog`, and `onRetryLaunchers`; WS07 still promises `SessionLauncher` and the shorter initializer. WS02's receipt omits the retry/catalog wiring (WS04 `:1312`, `:1315`; WS07 `:879`; WS02 `:798`).
   **Concrete fix:** use the providers' current exact signatures, accept M-04-3–7 individually (especially `initialCarryOver`), and reconcile WS07's mode parameters with WS04/D21 before dispatch. Reference current mount IDs throughout; WS09's active-session receipt is M-09-5, not M4. No duplicate WS02 client members were found in the other specs; this finding concerns view/navigation mount contracts, not RPC ownership.

3. **BLOCKING — F6 ownership resolver, any server error releases held sends.** The revision says any `MantaError.server` during resolution means `.allowed`, because a box unable to list jobs could not have created one. That inference is false: an existing box/job can have a transient server-side read failure. The resulting `.allowed` transition drains durable held prompts into a background job. **Evidence:** WS02 `02-chat-cards-queue.md:411`, `:421–426`; `mobile/native/MantaUI/MantaAPIClient.swift:923–929` maps every nonempty RPC `error` string to this same error case, not just unsupported-channel errors. `src/server/rpc.mjs:2434–2435` performs a live job-list read. **Concrete fix:** retain `.resolving` on generic server errors, with retry/reconnect feedback. If compatibility with an older box is required, pin a specifically verified unsupported-channel discriminator; do not infer capability absence from the error class. Replace the current “server error → allowed” test with a transient-error case that proves no held prompt is delivered.

4. **SHOULD — F10, “Load earlier” contradicts clear-focus window reset.** `clearFocus()` restores the 30-message initial limit, but `clearFocus(keepPosition:true)` is also described as expanding the slice to the full loaded window without a jump. If it shares that reset/refetch, a target 120 messages back disappears immediately and this is a tail replacement, not a prepend. **Evidence:** WS02 `02-chat-cards-queue.md:607–615`; `mobile/native/MantaUI/ChatSessionStore.swift:253`, `:523–530` define the initial limit and widening behavior. **Concrete fix:** specify that the keep-position variant preserves the current fetched limit/messages, removes only the local slice, and invokes normal widening when the target was already the first fetched message. Add a test for Load earlier at a deep focus and after the slice has index zero.

5. **SHOULD — F10, first mapped row is not necessarily the target message's row.** Taking the first row of the entire suffix assumes the target produces a visible block. An unfinished assistant message is skipped by the mapper; empty/unsupported messages can likewise yield no block. The next message is then highlighted as if it were the requested one. The fixed 500-message cap also reports an existing older search result as possibly compacted, rather than explaining the navigation limit. **Evidence:** WS02 `02-chat-cards-queue.md:578–596`; `mobile/native/MantaUI/ChatModels.swift:183–192` skips unfinished assistant messages; WS06 searches history beyond the current chat window. **Concrete fix:** specify a message-to-visible-row mapping or verify that the target produces a row with the same options before choosing its highlight; otherwise give accurate “not yet displayable” feedback. Distinguish cap exhaustion from missing/compacted history. Test a non-rendering target followed by a visible message and a valid target beyond the cap.

VERDICT: CHANGES REQUIRED
