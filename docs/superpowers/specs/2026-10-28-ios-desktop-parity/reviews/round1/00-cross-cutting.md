# Round 1 — cross-cutting seams

Evidence paths below are relative to the worktree; spec filenames are relative to this spec folder. Reviewed all ten workstreams against the master and searched the existing Swift/server code. These are integration findings, not per-feature reviews.

1. **BLOCKING — D2 / WS03 F7 / WS04 §12: three incompatible draft contracts remain.**
   - **Problem:** WS03 explicitly creates a second `NewSessionDraft` in `ComposerTextController.swift`, with nonoptional `cwd`, `[ComposerAttachment]`, only `Equatable`, and `carryOver`. WS04 consumes a different `Hashable, Sendable` type with optional cwd and `[NewSessionDraftAttachment]`. Neither workstream's pinned shape includes the master's `worktreeBranch` and `linkedIssueURL`. Following both specs produces a duplicate type and incompatible attachment consumers.
   - **Evidence:** `00-master.md:193-212`; `03-composer.md:533-557,602-606`; `04-sessions.md:927-964`. The current carry-over is separately defined in `mobile/native/MantaUI/HandoffStore.swift:27-31`; it is not the master's draft contract.
   - **Fix:** Copy D2's exact declaration into the wave-0 deliverable only; remove WS03's declaration and WS04's obsolete shape. Specify conversion between ready composer chips and `NewSessionDraftAttachment`, including the reverse conversion and defaults for both optional metadata fields. Explicitly implement those fields in WS04's prefill logic.

2. **BLOCKING — D2 / WS01 quote / WS05 inbox: producers bypass the agreed create-and-confirm flow.**
   - **Problem:** WS01 deliberately keeps Quote in new session on immediate fork creation. WS05 creates a worktree before handing off a draft and requires creation of a new project “without further prompts.” D2 instead requires the WS04 create sheet and one explicit Create confirmation. These are materially different workflows, not alternate spellings of the same API.
   - **Evidence:** `01-transcript.md:909-916`; `03-composer.md:549-553`; `04-sessions.md:942-975`; `05-git-pr-review.md:704-714,843-849`; `00-master.md:193-212`. Existing `mobile/native/MantaUI/ChatScreen.swift:968-993,999-1009` immediately calls the fork RPC for Quote in new session.
   - **Fix:** Have both producers call `navigator.startNewSession` with D2's draft. Route the quote callback change to the ChatScreen owner at a named integration point. For inbox, pass the intended branch and issue URL, defer worktree/session creation until Create, and remove the `forgeIssue`/no-further-prompts requirement (or explicitly amend D2 if issue association is still required).

3. **BLOCKING — D3 / WS03 Mount requests: the actual composer adoption is assigned to the wrong wave and owner.**
   - **Problem:** D3 assigns the additive ChatScreen adoption to WS03 in wave A. WS03 still assigns it to the orchestrator in wave 0 or WS02 in wave B, and excludes ChatScreen from its edited files. The wave-0 contract only promises signatures, not the completed controller/environment implementation. This leaves no single executable work assignment for adoption.
   - **Evidence:** `00-master.md:175-178,214-216`; `03-composer.md:563-579,581-594,635-637`. The current ChatScreen still owns plain composer state and seeds it directly (`mobile/native/MantaUI/ChatScreen.swift:264-269,297-309`).
   - **Fix:** State that WS03 performs all four mount edits in wave A, after implementing its controller, and add ChatScreen to its explicit D3 exception. WS02 must consume that completed adoption rather than keep an optional legacy binding fallback.

4. **BLOCKING — D5 / WS04 §6 / WS05 §4: the shared GitHub sign-in provider has three names and two implementations.**
   - **Problem:** D5 names `GitHubDeviceSignIn` in `CloneFromGitHub*`; WS04 provides `GitHubDeviceConnectView`/`GitHubDeviceConnectStore`; WS05 requires and creates `GitConnectGitHubSheet`/`GitDeviceFlowStore` and calls itself the sole provider to WS04. Its fallback asks WS04 to create WS05's files/API extension in wave A. This does not pin a usable provider contract or ownership boundary.
   - **Evidence:** `00-master.md:221-223`; `04-sessions.md:559-574,1066-1069`; `05-git-pr-review.md:437-442,769-777,856-859,887-891`.
   - **Fix:** Pick D5's canonical public view name and initializer, assign its view/store/pure logic/wire types/API methods/tests to WS04 in wave A, and remove their creation from WS05. WS05 should consume the exact same API in wave C. Update all filenames and package mount requests accordingly.

5. **BLOCKING — C5 / WS01 M3e / WS02 F11: command-frame consumer and provider disagree.**
   - **Problem:** WS01 requires `liveCommandsByMessageID: [String: OpencodeCommandOrigin]` and a command payload with optional arguments. WS02 publishes only `commandByMessageID: [String: StreamCommandExecutedPayload]`, with nonoptional arguments. WS01's exact mapper mount therefore references a property WS02 never promises to implement. The master also still says WS01 consumes step/truncation properties, whereas WS01 explicitly rejects that dependency.
   - **Evidence:** `01-transcript.md:897-901,919-922`; `02-chat-cards-queue.md:647-668,788-791`; `00-master.md:136-143`. The actual server emits `{messageID,name,arguments: args ?? ""}` (`src/server/streamInterp.mjs:1037-1040`).
   - **Fix:** Pin one map name and value type in C5 and both specs. Prefer retaining the server-shaped payload in WS02 and explicitly specifying WS01's conversion into its mapper input. Remove the duplicate decoder request. Record transcript-derived footer data as an accepted C5 amendment, and list all WS01 mapper/media mounts as WS02 deliverables.

6. **BLOCKING — C1 / WS04–09 and WS05–10: duplicate client methods are assigned to separate extensions.**
   - **Problem:** WS04 owns `usageStoppedList()` and expressly forbids a second copy, but WS09 lists the same method in its new extension. WS10 builds `forgeStatus()` in wave A with validation enabled; WS05 builds the same zero-argument name in wave C with validation disabled and different return-type names, while forbidding WS10's copy. Separate extension files do not isolate Swift members; these contracts create duplicate or ambiguous members and disagree on behavior.
   - **Evidence:** `04-sessions.md:1032-1036,1070-1072`; `09-models-usage.md:907-908`; `05-git-pr-review.md:50,861-862`; `10-settings-box.md:742`. Actual handlers distinguish the forge validation argument (`src/server/rpc.mjs:952`) and expose one stopped-list response (`:2394`). C1 helpers already exist with internal visibility (`mobile/native/MantaUI/MantaAPIClient.swift:944-977`).
   - **Fix:** Keep stopped-list decoding/method ownership in WS04 and explicitly consume it in WS09. Choose one wave-A owner for forge status, pin one wire type and `forgeStatus(validate:)` signature, and make WS05/WS10 share it; alternatively use explicitly distinct names. Audit the final extension-member inventory before dispatch, not just filenames.

7. **BLOCKING — Waves / WS06–07–09 mounts: wave B contains shared-file edits without an integrator.**
   - **Problem:** WS06 is explicitly instructed to edit SessionListView in wave B, while WS09's stopped-count mount needs the same file in that wave. WS07 explicitly edits MantaAppRoot in wave B, while WS09 adds its stores, overlay and sheet to that same root. Naming the original wave-A owner in a mount table does not schedule that owner to return. Letting each later-wave requester apply its mounts violates the master's no-shared-file rule.
   - **Evidence:** `00-master.md:171-184,189-191`; `06-search.md:427-435`; `07-artifacts-cards.md:608-613`; `09-models-usage.md:937-940`; `04-sessions.md:1054`. The relevant root branch is real (`mobile/native/MantaUI/MantaAppRoot.swift:97-109`).
   - **Fix:** Add an explicit wave-B integration substep with one named owner for SessionListView and MantaAppRoot after WS06/07/09 land, or serialize named mount commits. Assign WS09's SettingsScreen mount in the same ledger. Remove requester permission to edit those files concurrently.

8. **BLOCKING — C4 / mount receipt: WS02 expressly refuses a same-wave mount and omits several required receipts.**
   - **Problem:** WS06 says WS02 applies the ChatScreen search mount in wave B, but WS02 says WS06 applies it in a later wave. WS02's receiving list also never accepts WS01's mapper/media/command integration or WS07's artifacts/webhooks callbacks; its “master's allowed mounts” promise is too narrow because those mounts are absent from C4's allowed list. WS07's receiving work omits WS01's display toggle, WS04's rename/mode rows and WS02's read-only guard. These can silently remain unmounted even when every worker completes its own file list.
   - **Evidence:** `02-chat-cards-queue.md:773-787`; `06-search.md:414-435`; `01-transcript.md:897-902`; `07-artifacts-cards.md:575,595-606`; `04-sessions.md:1051-1052`; `02-chat-cards-queue.md:770-772`; `00-master.md:123-134`.
   - **Fix:** Add a bidirectional mount ledger: request ID, provider symbol, receiving file, applying owner, prerequisite commit and integration wave. Explicitly assign all same-wave ChatScreen/ChatSessionStore mounts to WS02 and all overflow mounts to WS07 after provider commits. Assign WS05's ChatScreen/list/review mounts to a concrete wave-C applier rather than merely addressing workers from earlier waves. Correct WS02 M2's obsolete RootView reference to WS04's actual SessionListView handler.

9. **BLOCKING — WS04 §9 / WS09 F6: stopped-session state has conflicting ownership and a backward dependency.**
   - **Problem:** WS04 in wave A implements stopped-list fetching, refresh events, records and row decoration itself. WS09 in wave B creates another store and says WS04's marker *must* read its `isStopped`. Wave 0 does not stub this store, and no migration/mount is assigned to switch WS04's row logic later. Implementing both duplicates the read/refresh state; obeying WS09 literally makes wave A depend on wave B.
   - **Evidence:** `04-sessions.md:769-792,1070-1072`; `09-models-usage.md:705-715,950-955`; `00-master.md:175-180`. Existing per-session row state is owned by `SessionListStore`, consistent with the ownership table, rather than the proposed future usage store.
   - **Fix:** Choose one source of stopped records. Either keep WS04's provider and build WS09's resume presentation/actions on it, or scaffold a shared provider in wave 0 and give it one owner. If migrating in B, specify the exact later-wave owner/commit and removal of the original fetch/subscription, alongside finding 7's integration plan.

10. **SHOULD — D1 / C7: package and generated-project changes have no complete receiving schedule.**
    - **Problem:** D1 assigns Package.swift/project.yml to WS07 in wave B, but WS05 requests additions for files only created in wave C and still calls Package.swift unowned. Pre-adding nonexistent C sources in B is not a valid intermediate package; leaving it for WS07's completed job loses the request. Several workstreams independently say to regenerate and commit the same pbxproj.
    - **Evidence:** `00-master.md:189-191`; `05-git-pr-review.md:789-790,826-831`; `07-artifacts-cards.md:615-624`; `03-composer.md:577`; `06-search.md:407-408`. `mobile/native/Package.swift:39-77` uses explicit source lists, not automatic discovery; `mobile/native/AGENTS.md:85-94` declares pbxproj generated.
    - **Fix:** Assign package updates and one pbxproj regeneration per integrated wave to a named integration owner. Explicitly schedule WS05's package additions after its C files exist. Workers should supply source/test manifests, not concurrently regenerate the shared project.

11. **SHOULD — C4 / WS02 F9 / WS09 F8: two providers specify the same seat row differently.**
    - **Problem:** The master makes WS09 the data provider; WS02 says WS09 need not provide anything and defines `ChatCardSeatLine`, while WS09 supplies `UsageSeatLine`. They also specify different row rendering (secondary Text versus LabeledContent). This is redundant implementation and leaves the receiving mount ambiguous.
    - **Evidence:** `00-master.md:134`; `02-chat-cards-queue.md:568-578,702`; `09-models-usage.md:875-892,942`. The existing `AccountsStore.conversationSeat` already wraps the selector (`mobile/native/MantaUI/AccountsStore.swift:98-99`; `AccountsModels.swift:874-882`).
    - **Fix:** Name one helper and one row API. Either preserve C4 and have WS02 consume `UsageSeatLine`, or amend C4 to let WS02 use the existing conversation-seat projection and remove WS09 F8. Keep one test suite for this shared formatting behavior.

12. **SHOULD — C3 / D4 / D6: composer behavior remains inconsistently documented after consolidation.**
    - **Problem:** C3 advertises Void insertion/attachment methods and multiline quote formatting, while WS03 returns Bool and preserves the existing single-line quote format. D4 settles the latter but the primary contract is not updated. WS05 defines append as one newline, WS03 as a blank line, and WS03 still names `.replace` for send-failures despite D6 settling append. These discrepancies encourage client-specific formatting and ignored rejection feedback.
    - **Evidence:** `00-master.md:105-118,218-225`; `03-composer.md:467-505,605-606`; `05-git-pr-review.md:840-843,893-895`. Current quote construction uses `QuoteText.buildQuoteBlock` before insertion (`mobile/native/MantaUI/ChatScreen.swift:999-1009`).
    - **Fix:** Update C3 to WS03's final Bool-returning signatures and the accepted quote rule. Pin append spacing once, remove replace alternatives for failures, and require all attachment/insertion consumers to handle rejection consistently.
