# WS09 review — round1

1. **BLOCKING — F1, ModelsStore mutation success/failure contract.** The spec promises that Sub toggles take effect, every failure is surfaced, and nothing changes on failure, but the prescribed two-call operation cannot provide those guarantees. `config:update` persists the preference before reconciliation; reconciliation returns the old agent list on failure rather than throwing. Treating a resolved call as success can therefore display “Saved” while the agent remains dispatchable. Evidence: `src/renderer/ModelsCard.tsx:285-308`; `src/server/providers.mjs:803-823`; `src/server/rpc.mjs:860-861`. **Fix:** explicitly inspect the returned `SubagentDef[]` against the intended reconciliation outcome (respecting the existing reconcile rules), distinguish “preference saved; agent registration could not be applied” from total failure, and offer retry. Do not promise rollback or “Nothing was changed” after the config write succeeded. Add injected failure cases for config success + reconciliation failure and reload failure after success. This can use the existing surface without expanding D7.

2. **BLOCKING — F6, Apply enabled state.** “Update (disabled at 0)” prevents disarming the last armed conversation, including the common single-row case. It contradicts the acceptance criterion that unchecking an armed row removes it after Update. This is a desktop defect copied into the proposal: `src/renderer/UsageResumeModal.tsx:97-106,229-230` contains a disarm branch that the zero-selection button guard makes unreachable; `src/server/stoppedStore.mjs:181-189` supports the removal. **Fix:** enable Apply whenever `applyPlan` has at least one arm or disarm operation, including a disarm-only plan with zero selected. Test one armed row unchecked, all armed rows unchecked, and zero-selected/no-change. Report the desktop-only defect rather than editing its renderer, per D10.

3. **BLOCKING — F1, picker filtering and deprecated selection.** Filtering “before grouping” only covers the full catalogue. The cockpit renders `modelStore.recents` directly and applies a choice without that filter, so a hidden model remains selectable there. The deprecated union also must reach the selection guard, not only the disabled appearance: otherwise a desktop-opted-in row looks enabled but its tap does nothing. Evidence: `mobile/native/MantaUI/ModelPickerSheet.swift:217-240` (recents), `:303-306` (group pipeline), `:318-321` (local-only selection guard); `mobile/native/MantaUI/ChatModelStore.swift:259-266` (fast-target selection). **Fix:** enumerate every selection path—catalogue row, recent chip, fast twin—and apply the same effective visibility/opt-in policy. Specify that retaining the active model for display does not make hidden alternatives selectable. Require the combined opt-in set in both rendering and action guards. Add tests for a hidden recent, hidden fast target, and a deprecated model opted in on desktop being successfully selected on iOS.

4. **BLOCKING — F1/M5, silently failed deprecated opt-in.** M5 explicitly says a box write failure “keeps the local opt-in and logs.” The user sees the model enabled even though the shared opt-in was never saved, violating the no-dead/misleading-control rule and the cross-device acceptance criterion. The existing synchronous local-only method at `mobile/native/MantaUI/ChatModelStore.swift:276-281` is exactly the behavior being replaced, not a sufficient failure model for the new network operation. **Fix:** make the action awaitable with pending and visible failure states; persist/mirror the confirmed box value, or explicitly show that only this device changed and provide retry. Read the latest opt-in list before merging so a stale catalogue snapshot does not erase another device's opt-ins. Test rejected writes and concurrent additions. D1 already assigns this file to WS09, so remove the unresolved-owner wording in M5/Open question 2.

5. **SHOULD — F4, unconditional row disappearance after Confirm/candidate pick.** Confirm and candidate selection declare only `{catalogId}`; this does not supply missing endpoint prices or caching facts. Such a row legitimately remains ineligible after refresh, contrary to the success copy and acceptance criterion that every action removes it. Evidence: `src/shared/modelIdentity.mjs:78-88` explicitly keeps endpoint pricing separate from catalogue identity; `src/shared/autoEligibility.mjs:42-55` independently requires price and caching; `src/renderer/ModelsWeCouldntIdentify.tsx:328-352` filters by the complete eligibility result. **Fix:** remove the row only when the refreshed result omits it; otherwise keep it with the updated missing fields and say “Identity saved — still needs …”, offering the editor. Separate identity-only and fully completed declaration acceptance cases; test a candidate with no price/cache metadata.

6. **SHOULD — F6/F7/M3, box-switch lifecycle missing.** The two new singleton stores retain records, alert queues, active-session IDs, and usage baselines, but the spec defines only idempotent bind and reconnect behavior. The app can switch boxes without relaunching. Without a box-scoped reset, an old box's sticky alert can create a reminder on the newly paired box, and old stopped rows can remain visible while new reads load or fail. Evidence: `mobile/native/MantaUI/MantaAppRoot.swift:184-202` resets existing session state during pairing; `:235-240` begins an in-process box switch; `mobile/native/MantaUI/MantaAPIClient.swift:752-758` exposes live config requests rather than a persisted snapshot. **Fix:** specify an explicit box-identity lifecycle for both new stores (and the new catalogue reload state): clear old records/alerts/baselines/active session on unpair/switch, cancel or generation-reject old requests, then seed the new box before permitting actions. Add an exact MantaAppRoot mount request and tests with a late old-box response.

7. **SHOULD — F6/F7, reconnect and seed ordering are underspecified.** Both stores must refresh/reseed on reconnect, but the only cited interface is `addRawFrameHandler`, which does not report connection transitions. The existing reconnect callback is single-owner and already assigned to the session list; an implementer could overwrite it. Also, an initial `usage:list` response arriving after a newer `usage.updated` can overwrite the baseline and cause duplicate alerts. Evidence: `mobile/native/MantaUI/MantaEventStore.swift:421-432,464-466`; `mobile/native/MantaUI/SessionListStore.swift:681`; the safe published-connection pattern is documented at `mobile/native/MantaUI/ChatSessionStore.swift:710-727`. **Fix:** pin a Combine subscription to published connection state (or an explicitly coordinated mount), retaining the subscription and detecting disconnect→connect without taking the single-owner callback. Define initialization/reseed ordering so stale fetches cannot replace newer event state, and suppress transition alerts until a baseline exists. Add delayed-seed and reconnect-with-missed-update cases.

8. **SHOULD — F7, expired sticky alert can schedule the wrong reset.** Limit banners remain indefinitely, but action availability checks only for a reset timestamp and active chat. After that timestamp passes, tapping Remind still sends the past `fireAt`. The scheduler converts it to yearless cron and finds the next future match rather than preserving the original instant. Evidence: `src/server/schedule.mjs:258-266,277-284`. **Fix:** revalidate the reset instant at tap time, retire/update alerts when their window resets, and reject an elapsed reminder with visible “This window has already reset” feedback instead of creating a job. Include `now` in the pure reminder/action policy and test a sticky alert acted on after expiry. No server change is needed.

VERDICT: CHANGES REQUIRED
