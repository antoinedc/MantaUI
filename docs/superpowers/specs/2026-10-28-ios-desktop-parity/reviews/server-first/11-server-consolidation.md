# WS11 server-first review

1. **BLOCKING — D1/D3: capability discovery is not upgrade-exempt on the specified client path.**
   - Problem: D1 says both version paths are exempt and migrates iOS discovery to `serverVersion()`. That RPC is blocked during an upgrade. A freshly connected client cannot obtain `upgrade-view-1`, so the new gate can remain in capability-loading state or hide the recovery controls even on a capable box.
   - Evidence: spec lines 95–96, 127–137, 403–404; `mobile/native/MantaUI/MantaAPIClient+Settings.swift:20–22` calls `server:version` over RPC; `src/server/upgradeV2.mjs:82–90` exempts `/api/version`, not `/rpc`.
   - Fix: explicitly load capabilities through the authenticated, upgrade-exempt `/api/version` path on both clients (reuse the existing version transport), and define failure/retry state rather than interpreting transport failure as an old box. Test a fresh client connecting while migration is running and while failed, with Retry/Rollback reachable when allowed.

2. **BLOCKING — D5: moving name selection to the server does not make concurrent creates unique.**
   - Problem: the specified read-live-names → choose → create sequence still races. Two requests can both choose `next_js`; the acceptance criterion promises that neither fails, but no serialization/reservation/retry is specified.
   - Evidence: spec lines 541–546 and 604–605; `src/server/rpc.mjs:1244–1262` performs asynchronous creation and then metadata writes; `src/server/tmux.mjs:508–535` can create an opencode session before attempting the tmux create. A collision can therefore also strand that session.
   - Fix: specify a box-owned critical section covering generated-name selection and successful tmux reservation/creation (or a bounded collision retry that reuses/cleans up the already-created chat). Use the final name for metadata and all returned navigation fields. Add a concurrent-handler test with a barrier after the name read, not just pure naming tests. This is the small name-allocation guarantee already promised, not the deferred general atomic-create feature.

3. **BLOCKING — D7: `liveChildStatus` is not an authoritative running-child source.**
   - Problem: the new count is explicitly based on the interpreter's `liveChildStatus`, but it is set idle when a task tool completes, including a task that merely launched background work. Actual child execution events do not update that map. Removing the clients' derivation makes the advertised server status wrong while a background child continues running; the new aggregator also needs the parent graph for windowless descendants.
   - Evidence: spec lines 689–700; `src/server/streamInterp.mjs:489–503` marks the child idle on tool completion; `:337–341` updates only the executing session; `:909–915` records `childParent` and publishes `childSession`, a frame missing from the specified aggregator inputs. `src/renderer/chatUtils.ts:2150–2192` currently rolls actual running sessions up the parent graph.
   - Fix: derive counts/busy from authoritative session-running state plus the child-parent graph and delegate records; subscribe to relationship creation/deletion as well as running changes, and hydrate relationships/status on startup/reconnect. Define snapshot replacement/clearing semantics. Test a completed background-launch tool with its child still running, nested windowless children, parent idle before child completion, and reconnect without an open chat.

4. **BLOCKING — D8: deleting truncation copy leaves the retained live-footer path without its hint.**
   - Problem: D8 adds label/hint only to canonical message views, while explicitly preserving the live truncation adapter and old-box live badges. That adapter retains only the kind. The footer still needs the deleted `TranscriptTruncation.describe` to label and explain the live badge; canonical view data does not exist yet during the turn or on the old-box fallback.
   - Evidence: spec lines 854, 873–887, 889–892; `mobile/native/MantaUI/TranscriptTurns.swift:77–89` stores only messageID/kind; `TranscriptTurnFooterView.swift:72–97` calls `describe` for its button and popover; `src/server/streamInterp.mjs:887–894` emits kind/label/messageID, but no hint.
   - Fix: add hint to the live truncation frame, carry the server label/hint through the live adapter and footer model, and explicitly migrate the footer view. Pin an honest old-box fallback using the supplied label and no unavailable explanatory action (or static generic explanation). Add live-before-refetch and old-box XCTest cases, not only canonical decoding tests.

5. **BLOCKING — D11: the live run contract cannot preserve the specified prose/reasoning/run order on iOS.**
   - Problem: `toolRuns` transmits tool membership and summaries, but neither run-close state nor ordered boundary anchors. iOS does not refetch mid-turn and its existing renderer concatenates all live text into one final prose row. A sequence tool A → prose → tool B cannot be rendered in canonical order by merely switching `mergingLive` to the supplied run list. Likewise the client cannot tell whether the latest run was closed by prose when the close emits an unchanged summary. This contradicts the promised unchanged row order and canonical handover.
   - Evidence: spec lines 796–809, 820–823, 1122–1139, 1175–1184; `mobile/native/MantaUI/ChatSessionStore.swift:850–865` has one `hasTailContent` value, and `:894–925` appends the combined `inProgressText` after all live activity. `src/server/streamInterp.mjs:809–818` already supplies text/reasoning part IDs and message IDs that could serve as anchors.
   - Fix: pin an ordered live placement contract (part IDs/ordinals and boundary/closed information, or a server-produced ordered block descriptor) and migrate the iOS live-text placement with it. Explicitly wire `toolRuns` through `MantaStreamRouter`/`MantaSessionStreamState`: unknown stream subs are currently discarded (`MantaEventStore.swift:174–275,590–613`), so a decoder only in `ChatSessionStore` is insufficient. Test tool→text→tool→reasoning→tool, same-message boundaries, coalesced frames, and reconnect snapshots against canonical order and stable IDs.

6. **BLOCKING — D11: resetting the ledger at execution start disagrees with canonical run boundaries.**
   - Problem: canonical rule 3 lets a run cross a non-renderable/background-result user message, but the live ledger always resets at `session.execution.started` and always closes on `session.inbox.delivered`. Thus tool A → background completion → tool B can be one canonical run with ID A and a live run with ID B. This is ordinary background-job flow, not the explicitly accepted restart undercount.
   - Evidence: spec lines 1078–1081 versus 1115–1124; `src/renderer/toolActivity.ts:371–373` only closes on a renderable user message; `src/server/streamInterp.mjs:790–795` handles inbox delivery using its ID, without classifying the delivered content; `mobile/native/MantaUI/TranscriptRow.swift:70–76` derives the activity row identity from the run ID.
   - Fix: make execution boundaries and delivered-message classification identical between the canonical reducer and live ledger. Preserve/seed the preceding open run when canonical rules allow continuation, or explicitly change the canonical rule and document the identity/behavior change. Add event/canonical parity tests for background-result delivery and a hidden user message across two executions, including tail-window/load-earlier handover.

7. **BLOCKING — D11: latest message order is not latest run state.**
   - Problem: choosing the RunView on the latest transcript message can select stale state after an earlier message's tool changes. The splice updates only that earlier message; a later absorbed message still carries its older copy. The same issue occurs when a full fetch resolves after newer splices. Final refetch may repair it, but the specified live summary/failed/running status is wrong until then.
   - Evidence: spec lines 801–808, 1108–1110, 1138–1146; `src/renderer/hooks/useTranscriptState.ts:219–240` fetches and replaces only the changed message. Neither RunView nor `toolRuns` supplies a revision to resolve these copies.
   - Fix: add a monotonic ledger generation/revision to run snapshots and merge by revision, or consume the authoritative changed-run frames into one desktop run map and use message annotations only to seed it. Define fetch-versus-stream ordering and generation reset behavior. Test an earlier tool completing/failing after a later message has already contributed to the same run, plus out-of-order RPC responses.

8. **BLOCKING — D11: the synthetic ledger cannot produce the required delegate label from completion output.**
   - Problem: the spec adopts iOS's output-first delegate naming, but its synthetic part contains input/title/status only. The generated job name is learned from completion output; canonical parts have it, live ledger parts do not. The promised identical live/reloaded label is therefore impossible under the written shape.
   - Evidence: spec lines 1074–1077 and 1117–1120; `mobile/native/MantaUI/ToolActivity.swift:919–939` prefers the quoted job name from output; `src/shared/opencodeV2.mjs:199–216` includes completion output/error/metadata in canonical state; `src/server/streamInterp.mjs:493–500` has the completion output available.
   - Fix: specify retaining the descriptor-relevant canonical state on ledger updates, including output-derived delegate name (or retain normalized output internally), and keep raw activity disclosure data joined by part/call ID without re-deriving wording client-side. Add a delegate completion fixture whose generated output name differs from its input prompt; compare live and canonical activity fields.

9. **BLOCKING — D11 deletion list leaves a retained Swift type uncompilable.**
   - Problem: `ToolActivity.clip` is explicitly deleted while `TaskStatusResolver` is explicitly kept. The latter still calls the deleted method twice. Merely listing the file under EDIT does not specify which retained responsibility moves.
   - Evidence: spec lines 1166–1173; `mobile/native/MantaUI/ToolActivity.swift:919–939` (`TaskStatusResolver.delegateJobName`) calls `ToolActivity.clip` at lines 928 and 936.
   - Fix: explicitly remove/migrate `delegateJobName` and its wording-only helper dependencies to the server alongside the delegate descriptor; retain only the child/job status resolution portion of `TaskStatusResolver`. Grep all remaining callers and add the moved declarations to the guard. Verify both the app unit-test build and the Foundation package after deletion.

10. **SHOULD — D6: specify partial cleanup failures in the close result.**
    - Problem: cleanup and metadata failures are non-fatal, but the result only defines dirty/kept notices and a tmux-error branch. The existing desktop reports cleanup exceptions even when it proceeds with closing. The new wire should not silently lose this feedback or label a failed removal as removed.
    - Evidence: spec lines 626–636; `src/renderer/Sidebar.tsx:260–261,284–285,319–320,331–332` surfaces these errors independently of kill success.
    - Fix: add safe warnings/partial-outcome fields and pin how `removed`/`kept` are populated on exceptions and how both clients show warnings after a successful close. Test remove failure + successful kill, metadata failure, and repeated/shared worktree paths.

11. **SHOULD — D8–D11 payload guard needs a concrete reference-resolution contract.**
    - Problem: the accepted >30% fallback changes a full RunView to `{id}`, but the declared type and latest-message-wins rule still require summary fields. It does not say which message retains the complete value or how a tail window obtains a run whose owner was omitted. Also a segment array repeated across many messages can dominate payload size, so a single anecdotal session is a weak guard.
    - Evidence: spec lines 783–792, 1101–1111, 1397–1400; `src/server/opencode.mjs:512–515` limits/slices the window before the proposed annotation point.
    - Fix: pin `RunView | RunRef` (or a response-level run table), resolution rules, and owner-outside-window behavior before implementation; latest reference must not overwrite a full summary. Measure serialized bytes against the same slim baseline and include a synthetic long run with many reasoning segments, a 100-message tail, and widening the window.

12. **SHOULD — sub-step independence and its gates contradict the delivery order.**
    - Problem: ground rule 6 forbids later steps editing an earlier module, but D9–D11 necessarily extend D8's `transcriptView.mjs` and several earlier client/server modules. D8 advertises D9's media capability before media exists. D1 also asks its capability test to equal the entire master registry before later IDs have been implemented. These rules cannot all be satisfied by independently shippable steps.
    - Evidence: spec lines 43–45, 57–65, 162–165, 754–761; master D25 says IDs are appended by each sub-step.
    - Fix: explicitly permit incremental edits to shared integration/view modules; make the D1 expected registry stage-aware; either split the media capability from turns or declare D8+D9 one release-atomic unit rather than independently shippable. Require per-step typecheck/server tests/client compile checks, with the full suites at the combined gate.
