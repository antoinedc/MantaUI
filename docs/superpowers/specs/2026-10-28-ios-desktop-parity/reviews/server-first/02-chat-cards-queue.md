# WS02 review — server-first

Reviewed the revised SF-0…SF-5 contracts, desktop migration, iOS consumption, and master D23–D30 / canonical mount ledger against the current worktree. This is a specification review; no builds or tests were run.

1. **BLOCKING — Desktop migration: complete the actual consumer chain.**
   - **Problem:** The migration table changes the wire types and cards but misses existing intermediate projections and several consumers. Following it leaves retry copy discarded and explicit references to deleted helpers; the approval refusal cannot be accessed through the declared API type.
   - **Evidence:** `src/renderer/hooks/useSseBus.ts:593–615` reconstructs retry state field by field and drops `headline`, `caption`, and `body`. Its public state types at `:133–144` also lack the new retry/compaction/notice fields. The spec's hook row mentions session errors and compaction, not this retry projection. `src/renderer/SessionHeader.tsx:724,841,888` still calls `formatTokensCompact`, beyond the “two call sites” the spec instructs the worker to replace. `src/shared/api.ts:1553` and `src/renderer/api/httpApi.ts:1315–1316` declare approval results as `{ok:boolean}`, whereas the migration requires displaying `result.error` without adding that field to either declaration.
   - **Fix:** Explicitly migrate the retry projection and all hook state/setter/return types through to the card; replace **all five** SessionHeader formatter uses; add optional `error` to the desktop approval result contract and HTTP generic. Require a hook-to-card test with distinctive server headline/caption/body (not just a card given a fabricated view), an approval-refusal test, and typecheck covering the deleted exports. These are completion of the stated migration, not additional features.

2. **BLOCKING — F8 / SF-0: old-box inbox actions deliberately lose failure feedback.**
   - **Problem:** Only Edit last is capability-gated. F8 expressly leaves × enabled on an old box while deleting outcome classification and displaying only the absent `error`/`notice` fields; Send now / Wait have the same problem. An old box can return `unknown` with HTTP 200, leaving the row unchanged and the click silent. Refreshing the inbox cannot communicate whether cancellation was confirmed. This contradicts D24/D25's dependent-control gating and the no-dead-controls requirement.
   - **Evidence:** `src/server/rpc.mjs:1388–1419` returns the undecorated interpreter outcomes today. `src/shared/types.ts:2988–2994` contains no notice/error fields. `src/renderer/inboxState.ts:185–197,216–239` and `mobile/native/MantaUI/InboxModels.swift:249–271` explicitly report `unknown` and `delivered` today; the proposed deletion removes that feedback. F8 at `02-chat-cards-queue.md:584–590` specifies that × still works without a notice. The desktop migration likewise consumes only the new fields.
   - **Fix:** Gate cancellation and delivery-change controls, including their action entry points, on `chat-cards-1` for both clients, with the specified update-box explanation; do not restore the moved classification locally. Include the desktop keyboard Edit last callback in the gate, not only its button. Test absent/unknown capability plus old-shape `unknown` responses so no enabled action silently loses its verdict.

3. **BLOCKING — SF-5: cancellation does not guarantee an item to restore.**
   - **Problem:** The new server helper takes only the result and specifies `result.item.text` for a confirmed cancellation. The existing result allows a confirmed cancellation with **no item**, and the old desktop helper had a separate local-item fallback. Moving that helper while removing the fallback without defining the missing-item branch can throw after the message has already been cancelled, or silently remove the message without restoring it.
   - **Evidence:** `src/server/streamInterp.mjs:619–625` captures `before` from the snapshot and returns `{outcome:"cancelled", ...(before ? {item:before} : {})}`. `src/shared/types.ts:2988–2991` consequently makes `item` optional. `src/renderer/inboxState.ts:216–229` currently accepts a separate `item` and uses `result.item ?? item`; SF-5 removes that parameter and its proposed tests cover no missing-item cancellation.
   - **Fix:** Pin this branch explicitly. At minimum, when `restore:true` and a cancelled result lacks its captured item, return `restoreText:null` with a visible explanation that cancellation succeeded but text could not be recovered; never dereference an absent item or report a generic failed cancellation. Alternatively establish and test a server-side capture guarantee before cancellation. Add pure-helper and RPC tests for `cancelled` without `item`, including `restore:false`.

4. **SHOULD — SF-4 verification: test all guarded mutations and preservation of routing.**
   - **Problem:** The specified RPC integration coverage exercises only prompt refusal, while the integration agent must modify five handlers, including a currently synchronous compact handler and handlers with existing handoff/CTO routing. Pure `assertWritable` tests do not prove those mounts are installed correctly.
   - **Evidence:** `src/server/rpc.mjs:1344–1358,1388–1419,1968,2055–2074`; the SF-4 integration-test paragraph specifies only job lookup and prompt → 409.
   - **Fix:** Require a table-driven integration test for all five guarded channels, asserting status 409, the exact human error/code, and zero downstream mutation calls. Cover ordinary sessions and `correlation.kind === "work"` continuing through the existing route, plus preservation of the existing HandoffError response branch. Keep tests dependency-injected and sandboxed.

5. **NIT — SF-5 mount reference disagrees with the canonical ledger.**
   - **Problem:** SF-5 calls its inbox registration `M-02-srv-11`, but no such mount exists; the actual row is `M-02-srv-9`. The preceding SF-4 prose also says “M-02-srv-6…9” for delegate registrations although 9 is the inbox-copy registration.
   - **Evidence:** `02-chat-cards-queue.md:924,955` versus its mount table at `:1191–1195`; `00-master.md:574–577` assigns delegate registrations/guards/error transport to 6/7/8 and inbox copy to 9.
   - **Fix:** Replace the stale references with 6/7/8 and 9 respectively. The detailed mount table already matches the master and should remain authoritative.
