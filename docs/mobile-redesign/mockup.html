The answer to “why doesn't it look sleek”

I was drawing the wrong decade

You were right and the reason is specific. My mockups were a custom flat design system — bordered cards, opaque bars, hard dividers, uppercase micro-labels. That was correct for iOS 16. Apple replaced the entire design language in iOS 26 (September 2025) with Liquid Glass, and refined it again in iOS 27 this June. Nothing I drew was built on it.

What Liquid Glass actually is

Not a blur. Apple's own word is lensing — the material bends the content behind it the way real glass does, with specular highlights that track the shape, shadows that darken when they pass over text, and a glow that spreads outward from your fingertip onto neighbouring controls.

It's a real-time OS-rendered material. You can't paint it — you can only ask for it.

The two-layer model

Everything is now either content or controls.

  • Content layer — edge-to-edge, fills the whole screen, scrolls under everything. Never glass.
  • Controls layer — bars, sheets, menus, buttons. Floats above, made of glass, and the content is visible through it.

Bars no longer have backgrounds or dividers. A tab bar is a floating capsule inset from the edges that shrinks as you scroll.

Why this settles the RN question decisive

A webview cannot render Liquid Glass. It can imitate a frosted blur — and that's exactly what my “Elevated” direction was doing. It cannot do lensing, adaptive shadow, the light/dark flip against background luminance, the scroll edge effect, or the fingertip glow.

Going native isn't “nicer transitions” any more. It's the difference between being the platform and drawing a picture of it.

And React Native gets it for free. expo-glass-effect has shipped since SDK 54 (Sept 2025) wrapping the real UIVisualEffectView. More tellingly, Expo's own docs say navigation headers “adopt the system's Liquid Glass effect by default — it cannot be disabled per screen.” You have to work to opt out. Form sheets adopt it with no code changes. The native tab bar exposes minimize-on-scroll and the bottom accessory slot. Using native components is the design work.

Apple's guidance is to spend custom-component effort on one hero surface and use the system for everything else. For us that hero is the transcript.

Where consistency with desktop actually lives

Not in identical chrome — desktop can't have a floating glass tab bar and shouldn't try. It lives in the layer underneath: the same colour tokens, the same lucide icon set, the same status vocabulary (running / needs you / idle), the same session-header contents, the same transcript anatomy. That's also what the Design Award winners do: unmistakable brand in the content, stock platform chrome around it.

The product · 02 — you asked me to define this

Acting on a session

Your proposal was long-press for rename and delete, swipe for delete. That's the right shape. I'd change three things, and one of them matters a lot.

The proposal

GestureDoesReasoning
TapOpen—
Swipe left (trailing)Mute · Delete. Full-swipe commits Delete.Trailing is the destructive side by iOS convention. Two actions fit comfortably; three don't.
Swipe right (leading)Pin / Unpin. Full-swipe commits.Leading is the positive side. Pin is already a concept desktop introduced in this same redesign, so it costs nothing new and it's the action you take most after opening.
Long-pressNative context menu: Rename · Pin · Mute notifications · Fork · Copy path, separator, DeleteEverything, including both swipe actions. Apple: “always make context menu items available in the main interface too” — and destructive items go at the end of a context menu (the opposite of an action sheet, where they go at the top).

The three changes, and why

1 · Delete undoes, it doesn't confirm the one that matters

A confirm dialog on every delete makes the common case slow to punish the rare case. The modern pattern is the reverse: delete immediately, show an undo for five seconds, and only actually fire the RPC when the toast expires.

That's genuinely easy here — the deletion is one call we simply hold. It also means a full-swipe can commit safely, which a confirm dialog would make reckless.

2 · Except when the session is running

Deleting a running session kills a live turn and the work in it. That's not undoable by holding an RPC for five seconds, because the turn is already dead.

So: idle sessions delete with undo, running sessions confirm. The confirm names what's being interrupted — “this will stop a turn that's been running 4 minutes”.

3 · Mute is worth adding new concept

One noisy agent shouldn't cost you notifications from the other four. Today notification routing is global, so per-session mute is a small server-side addition — a set of muted session IDs consulted before a push fires.

It's the action most likely to be wanted at 2am, and it's the reason the trailing swipe has room for two things.

The product · 03 — first class, per your call

Terminal mode

It's a webview under every plan — and this is the one screen where that genuinely doesn't matter. A terminal is full-bleed with no navigation chrome, so there's nothing for the platform to render differently. What it does need is everything around the text, and today it has almost none of it.

Worth restating why the webview is fine here. Blink Shell — native Swift, the reference professional iOS terminal — renders its terminal through a JavaScript emulator in a webview by choice. Their stated reason is rendering fidelity and speed. A terminal emulator is a VT100/xterm state machine plus a high-throughput text renderer, and xterm.js is twenty years of accumulated edge cases we already depend on. The native work is the keyboard, gestures and chrome, and all of that sits outside the webview in React Native.

The plan — full replacement

You said no transition, we can nuke the existing client, and the epic should be a straight replacement. That's simpler in a way worth spelling out: it deletes work rather than adding a migration.

The test is mechanical: the native view layer imports zero DOM. Most of it already passes.

Two build decisions I'd lock in the epic

No NativeWind

The stable release pins Tailwind v3, and v4 support has sat in a preview marked not-for-production since September 2025. It also bakes colour opacity statically, which fights variable-driven theming.

Instead: the token module feeds a typed theme, and styles are plain objects. That's better than class strings on both platforms and it removes a dependency that would gate our design system on someone else's release schedule.

Our own markdown renderer

The leading React Native markdown library hasn't published to npm since December 2023; the leading syntax highlighter died in 2019. But we don't need a general one — we control the markdown the agent emits.

A purpose-built renderer streams by block without re-parsing the document, and makes tool cards, diffs and todo lists first-class node types instead of HTML we style afterwards. Parsing is shared with desktop; only the rendering differs.

Reference

Pairing — what the link grants

Unchanged from the last round, kept here because it's the security spine of onboarding. The payload grants command execution on a machine the user owns, and there's a published, state-actor-operated attack against exactly this flow shape.

Already right today

  • Short-lived single-use nonce, not a bearer token
  • The code is generated by the already-authenticated side and claimed by the joiner — structurally safer than Signal's, where the QR grants access

Missing today

  • Any screen naming what's being linked
  • Out-of-band code comparison
  • A linked-device list with revoke
  • A notification to existing devices when a new one appears — the push pipeline already exists
  • Idle expiry on device tokens

In February 2025 Google's threat-intelligence group published a campaign in which Russia-aligned actors abused Signal's linked-devices feature at scale: fake “group invite” pages swapped the redirect for a device-linking URL pointing at an attacker-controlled instance, so the victim's own device performs the link. Malicious QRs were disguised as group invites, security alerts, and Signal's own pairing instructions. Their assessment of why it worked: “a low-signature form of initial access due to the lack of centralized, technology-driven detections… a compromise can go unnoticed for extended periods.”

App Clips — the follow-up you asked for

An App Clip is a slice of the app under 15 MB that iOS runs without installing anything, launched from a QR. It pairs for real, writes the token to a shared keychain or App Group container — which Apple documents for precisely this case — and the full app reads it on first launch and opens straight to the session list. No second scan. It's the only Apple-sanctioned way to carry a credential through an App Store install.

It cannot be built before the app is live on the App Store: default and demo App Clip links can only be tested once the app and clip have passed review. So it's a follow-up issue by necessity, not by preference. Two constraints to note when it's written: the 100 MB size tier explicitly forbids QR and App Clip Code launches, so the budget really is 15 MB; and Android has no equivalent, since Google shut down Instant Apps — the web fallback page has to exist regardless.
